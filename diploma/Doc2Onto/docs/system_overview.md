## 1. Тема ВКР и суть системы

Тема: «Разработка системы автоматизированного пополнения онтологической
модели кафедры знаниями, извлечёнными из документов».

Doc2Onto — настольное (desktop) приложение, которое умеет:
- принимать на вход документы кафедры (DOCX, DOC, PDF) — заявления,
  индивидуальные задания на практику, отчёты, тезисы конференций и т. п.;
- приводить их к **унифицированному формату представления документов
  (UDDM)** — структурированному XML-дереву, в соответствии с идеей 
  разделения «данные ↔ знания»;
- классифицировать документ, выбирая соответствующий **шаблон**;
- извлекать поля документа гибридным методом «детерминированный DSL +
  LLM-уровень», нормализовывать значения **концептами**;
- собирать из значений **черновой граф знаний**, показывать его
  пользователю и позволять править вручную;
- сливать результат в **общую онтологию кафедры** с учётом политик
  слияния, заданных в схеме онтологии.

## 2. Технологический стек

- **Язык**: Python 3.11.
- **GUI**: PySide6 (Qt 6) — настольное приложение.
- **RDF**: rdflib 7.6 — внутренний граф, парсинг/сериализация Turtle,
  работа с IRI/Literal/Namespace.
- **Парсинг DOCX**: python-docx, lxml; внутренний конвертер ходит по
  `word/document.xml` через ElementTree.
- **DOC → DOCX**: внешние движки — LibreOffice headless или Microsoft
  Word через COM (pywin32). Сделано как fallback-цепочка.
- **PDF → DOCX**: реализовано (нормализатор `pdf_to_docx`) через ConverAPI.
- **Морфология русского языка**: pymorphy3 — приведение ФИО к
  именительному падежу при идентификации персон.
- **LLM**: OpenAI Python SDK (`openai`) — обращение к OpenAI Responses API.
  Дефолтная модель — задаётся в `app/settings.py` константой
  `DEFAULT_MODEL`.
- **Вспомогательное**: pydantic (DTO), Jinja2 / markdown2 / Pygments
  (рендер шаблонов и подсветка кода в UI), `python-dotenv` (env), `tqdm`.

## 3. Структура репозитория

Полная структура есть в `README.md`. Ключевые места:

- `main.py` — точка входа.
- `app/` — оркестрация: `pipeline.py` (последовательность стадий),
  `context.py` (singleton-контейнер: логгер, менеджеры документов и
  шаблонов, репозиторий онтологии), `agents.py` (вызовы LLM), `settings.py`
  (пути и константы), `logger.py`.
- `models/` — DTO: `Document`, `Template`, `ExtractionResult`.
  `Document.Status` — enum состояний документа в pipeline (UPLOADED,
  UDDM_EXTRACTED, CLASS_DETERMINED, FIELDS_EXTRACTED, TRIPLES_BUILT,
  ADDED_TO_MODEL).
- `modules/` — стадии pipeline (см. раздел 4).
- `core/` — ядро, доступное коду шаблонов: `uddm/` (модель документа +
  XSD-схема), `fields/` (Field/Selector/Extractor/Normalizer),
  `concepts/` (концепты), `graph/` (DraftGraph, EditedGraph,
  TemplateGraphBuilder), `template/` (BaseTemplateCode + структурная
  валидация шаблона).
- `storage/` — менеджеры документов и шаблонов; `OntologyRepository` —
  чтение TBox, журнал слияния, история документов.
- `ui/` — три основных вкладки: `documents/`, `templates/`,
  `ontology/`. Внутри `documents/view/` — три суб-вкладки документа
  (оригинал, UDDM, граф).
- `resources/` — `onto/schema.ttl` (схема онтологии), `prompts/`
  (системные/пользовательские промпты для всех LLM-вызовов),
  `template/code_example.py` (пустой код шаблона).
- `.data/` — динамические данные, создаются при работе:
  `documents/<id>/`, `templates/<id>/`, `ontology/` (schema.ttl,
  history.json, ontology.ttl, facts.jsonl), `logs/`.

## 4. Конвейер обработки документа

Pipeline собран в `app/pipeline.py` как цепочка из пяти стадий, каждая
переводит документ из одного `Status` в следующий:

| # | Стадия | Класс | Вход | Выход | Когда может упасть |
|---|---|---|---|---|---|
| 1 | conversion | `Converter` | оригинал | UDDM | формат документа не поддерживается |
| 2 | classification | `Classifier` | UDDM + название документа + метод classify шаблона | класс документа | нет подходящих шаблонов |
| 3 | extraction | `Extractor` | UDDM + метод fields шаблона | значения полей | только в непредвиденных ситуациях |
| 4 | graph_building | `GraphBuilder` | значения полей + метод build шаблона | DraftGraph | только в непредвиденных ситуациях |
| 5 | model_insertion | `Connector` | DraftGraph + правки | запись в онтологию | не все поля были извлечены |

pipeline **возобновляемый**. Если документ остановился
на стадии 2 (класс не определился), при повторном запуске стадии 1–2
не выполняются — статус документа сохранён. При этом пайплает построен так,
чтобы не падать в произвольный момент. Если формат документа поддерживается 
и класс документа определён, пайплаин 100% дойдёт до конца или до предпоследней
стадии (в случае неполноты графа). Пользователь может редактировать только
класс и результат построения графа (промежуточные данные не редактируются)

### 4.1. Стадия Converter

Реестр трёх типов преобразований:

- **Normalizers** (`modules/converter/normalizers/`) — lossless-пред-
  обработка между форматами. Сейчас: `doc → docx`, `pdf → docx`. Применяются
  рекурсивно, пока формат не стабилизируется.
- **Internal converters** (`modules/converter/internal/`) — DOCX → UDDM,
  основной путь. Собственный ElementTree-парсер ходит по
  `word/document.xml`, узнаёт абзацы, нумерованные/маркированные списки
  (по `<w:numPr>`), вложенные таблицы. Заголовки определяются по стилям
  и эвристикой «короткий + жирный + центрированный». Тобеж информация о
  структуре берётся напрямую из скелета word-овского файла.
- **External converters** (`modules/converter/external/`) — slot для
  внешних IDP/OCR-извлекалок, которые выдают свой формат и адаптируются
  к UDDM. Каркас на месте, конкретных реализаций пока нет.

Кроме UDDM конвертер также сохраняет три «обратных» представления
(`reverse/`): plain text, HTML и tree-view — они нужны UI и логированию.

### 4.2. Стадия Classifier

Простая, но осознанно простая: перебирает все шаблоны и для каждого
вызывает `code.classify(doc_name, uddm) -> bool`. Возвращает первый
True. Конкуренции нет: предполагается, что шаблоны взаимно исключают
друг друга. Даже если класс не определился или определился неправильно,
пользователь может его указать явно (это не проблема).

### 4.3. Стадия Extractor

Состоит из трёх под-этапов в одном модуле (`modules/extractor.py`,
класс `Extractor`):

1. **Декларативное извлечение** — для каждого поля шаблона
   запускает `field.selector._select(uddm)` (находит определённый элемент UDDM) 
   и `field.extractor._extract(text)` (приводит простую предобработку строкового 
   представления найденного элемента UDDM). Результат сохраняется в
   `value_temp`/`error_temp`.
2. **LLM-проверка/коррекция** — отправляет один запрос к LLM, в payload
   которого попадают: UDDM-документ как XML-строка целиком + список всех
   полей шаблона с их `name`, `description`, и тем, что дал шаг 1.
   Системный промпт инструктирует модель: подтвердить уже извлечённое
   значение, исправить его, либо найти заново. Контракт ответа — JSON
   `{field_name: {status, value, error}}` со строгой комбинаторикой
   сценариев. Результат — в `value_llm`/`error_llm`.
3. **Нормализация** — для каждого поля прогоняет «raw»-значение
   (LLM в приоритете, fallback на template) через
   `field.normalizer._normalize(raw)`. Результат — каноническая строка в
   `value_normalized` (это и есть то, что увидит builder) или
   `error_normalized` с причиной.

GraphBuilder работает только с `value_normalized`.

### 4.4. Стадия GraphBuilder

`modules/builder.py`, класс `GraphBuilder`. Создаёт `TemplateGraphBuilder`
с готовым словарём `field_values: Dict[str, str]`, передаёт его в
`code.build(b)` шаблона. Получившийся `DraftGraph` сохраняется в
`draft_graph.json`. При исключении внутри `code.build(b)` стадия
сохраняет частично построенный граф и пишет отдельный `build_error.json`
с трассировкой и контекстом — это инструмент для диагностики авторов
шаблонов. Все ручные правки графа (`draft_graph_edits.json`,
`supplementary_facts.ttl`) при перезапуске стадии **сбрасываются** —
правки имеют смысл только относительно последнего успешного черновика.

### 4.5. Стадия Connector

`modules/connector.py`, класс `Connector`. Применяет ручные правки
(`EditedGraph.load(draft, edits_path)` + `build_modified_graph()`),
подмешивает дополнительные факты (`supplementary_facts.ttl`),
вызывает reconciler (опционально, если установлен), и затем зовёт
`OntologyRepository.merge_document(...)`. Репозиторий сам:

- читает текущую сборку онтологии;
- определяет `effective_date` документа (берёт из извлечённых полей
  даты по приоритетному списку);
- применяет к каждому новому факту политику слияния по аннотации
  `:mergePolicy` соответствующего предиката;
- пишет результат как отдельный фрагмент TTL под id документа в
  `.data/ontology/`, добавляет запись в `history.json`, событие в
  `facts.jsonl`.

Полная актуальная онтология собирается «лениво» из схемы + истории
фрагментов через `OntologyRepository.assemble_full_graph()` с
кешированием по фингерпринту истории.

## 5. Унифицированная модель документа (UDDM)

UDDM — это сознательно минимальное иерархическое представление
документа. Объектная модель в `core/uddm/model.py`:

```
UDDM
└── root
    └── block*                  ← прямые дети документа
         ├── Text               ← блок параграфов
         │    └── P+            ← атомарный параграф (только он несёт текст)
         ├── ListBlock
         │    └── Item+
         │         └── block+
         └── Table
              └── Row+
                   └── Cell+
                        └── block+
```

Принципы:

- **Минимальность.** В UDDM нет шрифтов, секций, колонтитулов, цветов.
- **Форматная независимость.** Один и тот же документ в DOCX, DOC, PDF
  должен попадать в один и тот же UDDM (на практике совпадение точное
  для DOCX/DOC, потому что DOC сначала нормализуется в DOCX; для PDF
  ожидается приближённое совпадение).
- **Иерархичность.** Только дерево, без форвардных ссылок.
- **Детерминированность.** Один и тот же файл всегда даёт один и тот же
  XML.
- **Ориентированность на шаблоны.** Структура подобрана так, чтобы её
  было удобно сужать селекторами (см. ниже).

XSD-схема — в `core/uddm/schema.xsd` (в репозитории). Конвертер
сохраняет UDDM как UTF-8 XML (без префиксов namespace в текущей версии).

В тексте ВКР важно подчёркивать, что **`p` — это атомарный параграф**, а
**`text` — контейнер связных параграфов**: формулировка «текстовый блок»
без уточнения чревата путаницей. `text` не супер полезен в правилах
шаблона, но он разбивает сплошной текст, состоящий из параграфов, на
логические единицы (например по разделам, отделённых заголовками). 

## 6. Шаблон и его контракт

Код шаблона — это пользовательский Python-модуль (`code.py` внутри
`.data/templates/<id>/`), реализующий абстрактный класс
`core/template/base.py:BaseTemplateCode` с тремя методами:

```python
class BaseTemplateCode(ABC):
    def classify(self, doc_name: str, uddm: UDDM) -> bool: ...
    def fields(self) -> List[Field]: ...
    def build(self, b: TemplateGraphBuilder) -> None: ...
```

- `classify` — определяет, его ли это документ.
- `fields` — описывает, какие поля шаблон извлекает (см. раздел 7).
  Поля — это **декларация**, по ней работает экстрактор и LLM-fallback.
- `build` — **императивная** часть: получая значения полей, шаблон
  собирает граф через builder.

То есть шаблон сразу несёт три знания: критерий классификации, набор
извлекаемых полей и алгоритм сборки графа.

Для кода шаблона есть структурная валидация (`core/template/validation.py`),
проверяющая шесть категорий (`structure`, `security`, `fields`,
`classify`, `build`, `ontology`):
- AST-проверка кода: запрет на `os/subprocess/socket`, `open`, `exec`,
  `eval`, `__import__`, `__subclasses__` (см. `_ALLOWED_IMPORT_ROOTS`).
- Динамические dry-run-вызовы `classify` на пустом UDDM и `build` с
  фиктивными значениями всех полей.
- Сверка обращений `ONTO.<имя>` с локальными именами в схеме онтологии.

Отдельной «песочницы» (sandbox) исполнения нет: шаблон **выполняется в
основном процессе приложения**. Защита от вредоносного кода — через AST-
анализ при загрузке. Этот компромисс надо упоминать честно: «безопасность
шаблонов обеспечивается ограничением набора допустимых импортов и
синтаксических конструкций». sandbox - место для улучшения.

## 7. Поле шаблона и DSL извлечения

**Поле** — это именованная декларация одного атомарного значения, извлекаемого 
из документа. Объект `Field` в `core/fields/field.py` содержит:

- `name: str` — snake_case-имя, используется как ключ значения, как
  диагностический идентификатор и как поле в LLM-запросе;
- `description: str` — естественно-языковое описание; именно его видит
  LLM при fallback и проверке;
- `selector: FieldSelector` — какой узел UDDM содержит значение;
- `extractor: FieldExtractor` — как из текста узла достать «сырую» строку;
- `normalizer: FieldNormalizer` — как привести «сырую» строку к
  каноничной форме (или отвергнуть).

То есть поле — это **четвёрка** «что найти, чем извлечь, чем
нормализовать, как объяснить LLM». Эта четвёрка же является единицей
гибридной экстракции: каждое поле проходит DSL → LLM-fallback →
нормализатор; статусы и ошибки считаются по полю.

Жизненный цикл значения поля:

```
declare(name, description)
   ↓
selector(uddm)  →  text          (FieldSelector)
   ↓
extractor(text) →  raw_value     (FieldExtractor)
   ↓
[если raw_value пуст / неправильно извлёкся → LLM может предложить значение]
   ↓
normalizer(raw_value)  →  canonical | None  (FieldNormalizer)
   ↓
builder использует canonical
```

Определение полей специально сделано динамически через метод fields,
чтобы дать потенциальную возможность создавать переменное количество полей.
В 95% сценариев это не нужно, но полезно в плане гибкости.

### 7.1. FieldSelector

Декларативный путь по дереву UDDM. Цепочка операций:

- `find(element_type, predicate)` — поиск элементов (`P`, `Text`,
  `Table`, `Cell` и т. д.) по типу и предикату;
- `next_element() / previous_element() / inner_element(idx) /
  outer_element()` — навигация по соседям/детям/родителю;
- `first() / last() / at(idx)` — выбор из множества подходящих элементов;
- `between_markers(left_pred, right_pred)` — срез между двумя якорями
  (особенно удобно при «вытаскивании» однотипных подразделов);
- `apply(custom)` — пользовательская операция.

Селектор начинает с корня UDDM и сужает «scope» на каждом шаге. На
выходе — либо одна локальная область (превращается в строку), либо
несколько (берётся первая). Пример: find(ElementType.CELL, 
Predicate.contains_text("оценка")) может найти несколько клеток,
содержащих "оценка". В данном случае эти клитки - локальные области
поиска. Если продолжить цепочки ещё, то общая область поиска будет сужаться.

Предикаты собираются через статический класс `Predicate` (раздел 7
плана файла): `contains_text`, `matches_regex`, `starts_with`,
`ends_with`, `min_length`, `max_length`, `all_of`, `any_of`, `invert`,
`always_true`.

### 7.2. FieldExtractor

Цепочка строковых преобразований: `regex`, `after`, `before`, `between`,
`replace`, `normalize_spaces`, `trim`, `prefix`, `suffix`, `lower`,
`upper`, `keep_letters_and_spaces`, `keep_digits_and_symbols`,
`keep_regex`, `strip_template_markers` (специально для подписей вроде
`(Ф.И.О.)`, `(подпись)`, `(дата)`, длинных подчёркиваний),
`pick_first_match` (несколько шаблонов по приоритету), `apply`
(custom).

Возвращает строку или `None`. Не делает онтологически-зависимых
преобразований — это работа нормализатора через концепт.

### 7.3. FieldNormalizer

Раньше был `FieldValidator` («проверить — вернуть ошибку») и отдельный
`ValueTransformer` («преобразовать к канонике»). Эти два слоя были
сведены в один `FieldNormalizer`: вход — строка, выход — каноническая
строка либо `None`. Это устраняет противоречие, при котором валидатор
сообщал «ФИО не в именительном», а трансформер ниже по pipeline всё
равно его исправлял.

Универсальный метод нормализатора — `concept(BaseConcept)`: делегирует
нормализацию в подкласс концепта. Это **единственный путь** привязать
поле к онтологии. Дополнительно есть форматные проверки/преобразования:
`integer`, `numeric`, `in_range`, `less_than`, `greater_than`, `regex`,
`alphabetic`, `word_count`, `min_length`, `max_length`, `lowercase`,
`collapse_spaces`, `replace`, `apply`.

### 7.4. Идиомы DSL внутри шаблона

```python
# Строитель (в общем случае)
b.field("student_email").literal()                          # литерал-строка
b.field("student_email").part(EmailConcept, "domain").literal()  # часть концепта
b.individual("student_full_name", PersonConcept,
             role=ONTO.Студент)                             # индивид с ролью
b.literal("application_date", DateConcept)                  # типизированный литерал

# Композитные хелперы
b.thesis(student=...)                                       # ВКР: IRI = hash(student)
b.practice(student=..., start_date=...)                     # Практика: IRI = hash(student|date)
b.direction(code_field=..., name_field=...)                 # Направление подготовки
```

Существенное архитектурное соображение: builder **не выбрасывает
исключения**. На любую ошибку (пустое поле, несоответствие концепта,
кривое значение) он возвращает «неполный» `DraftNode` с заполненным
полем `error`. Эти ошибки потом видны пользователю в UI как
«неполные триплеты».

## 8. Концепты и identity-модель

Концепт (`core/concepts/base.py:BaseConcept`) — модуль, который
инкапсулирует ВСЁ знание о конкретном элементе онтологии: как разобрать
сырое значение, как вычислить каноническую форму, как назвать IRI
индивида и какие литералы добавить в граф вместе с ним.

Контракт концепта (stateless, методы — class-методы):

```python
class BaseConcept(ABC):
    name: ClassVar[str]                        # snake_case-имя
    kind: ClassVar[ConceptKind]                # CLASS_INDIVIDUAL | DATATYPE
    onto_class_local: ClassVar[Optional[str]]  # имя класса в схеме

    @classmethod
    def parse(cls, raw: str) -> ConceptParts: ...        # парсинг на составляющие, полезные в построении нод графа
    @classmethod
    def normalize(cls, raw: str) -> str: ...             # canonical (через parse)
    @classmethod
    def is_valid(cls, raw: str) -> bool: ...             # проверка, можно ли распарсить
    @classmethod
    def iri_local(cls, parts: ConceptParts) -> str: ...  # IRI (для CLASS_INDIVIDUAL)
    @classmethod
    def build_triples(cls, parts, *, subject) -> Sequence[DraftTriple]: ...
```

`ConceptParts` — `dataclass(frozen=True)` с двумя полями: 
`canonical` — каноническая строка, представления концепта и 
`parts: Mapping[str, Optional[str]]` — именованные части
(например, `last_name/first_name/middle_name/sort_key` для Персоны).

Свойство, на которое стоит сослаться: **идемпотентность**. Контракт
требует, чтобы `parse(parse(x).canonical)` давал тот же `canonical`.
Без этого pipeline теряет повторяемость: при повторном проходе
концепт мог бы выдавать другой IRI.

### 8.1. Реестр концептов (`core/concepts/__init__.py`)

| Концепт | kind | onto-класс | Стратегия IRI / канонизации |
|---|---|---|---|
| `PersonConcept` | CLASS_INDIVIDUAL | `:Персона` | morph→именительный; `Персона_<sha1>(lower(фамилия)\|инициал_имени\|инициал_отчества)` |
| `OrganizationConcept` | CLASS_INDIVIDUAL | `:Организация` | хеш от нормализованного названия |
| `GroupConcept` | CLASS_INDIVIDUAL | `:Группа` | без хеша: `Группа_<номер>` |
| `DirectionConcept` | CLASS_INDIVIDUAL | `:НаправлениеПодготовки` | `Направление_XX_XX_XX` (точки в коде → подчёркивания) |
| `ProfileConcept` | CLASS_INDIVIDUAL | `:Профиль` | хеш от нормализованного названия |
| `ThesisConcept` | CLASS_INDIVIDUAL | `:ВКР` | хеш от локального имени IRI студента |
| `PracticeConcept` | CLASS_INDIVIDUAL | `:Практика` | хеш от пары `(студент, ISO-дата начала)` |
| `PositionConcept` | CLASS_INDIVIDUAL | `:Должность` | named-individual из закрытого перечисления (`Должность_Доцент` и т. п.) |
| `DegreeConcept` | CLASS_INDIVIDUAL | `:УченаяСтепень` | то же |
| `TitleConcept` | CLASS_INDIVIDUAL | `:УченоеЗвание` | то же |
| `GradeConcept` | CLASS_INDIVIDUAL | `:Оценка` | то же |
| `EmailConcept` | DATATYPE | — | `xsd:string`, нормализованный |
| `TelephoneConcept` | DATATYPE | — | `xsd:string`, нормализованный |
| `DateConcept` | DATATYPE | — | `xsd:date`, ISO `YYYY-MM-DD` |

Перечисляемые концепты (Должность, УченаяСтепень, УченоеЗвание, Оценка)
устроены так: внутри концепта — таблица синонимов («в.н.с.» → ведущий
научный сотрудник, «к.т.н.» → кандидат технических наук и т. п.), `parse`
матчит вход с одной из ячеек, IRI получается префиксом класса +
канонической формой, литералы — пустые (NamedIndividual уже всё
описывает в схеме).

Композитные концепты (Practice, Thesis) сделаны намеренно: «слабые
сущности» (события) идентифицируются связкой со студентом + временем.
Без этого пара заявлений на разные практики одного студента
схлопнулась бы в один индивид.

### 8.2. Эволюция: концепт `ВидПрактики` удалён

Изначально вид практики был концептом-перечислением (Учебная,
Производственная, НИР, Эксплуатационная, Преддипломная) с собственным
classом и связью `:видПрактики`-as-ObjectProperty. Реальные документы
постоянно ломали маппинг — словосочетания типа «производственной
практики (научно-исследовательской работы)» в родительном падеже не
матчились на нормализованные синонимы. Было принято решение **отказаться
от закрытого словаря**: вид практики теперь свободная строка
(`:видПрактики` — DatatypeProperty `xsd:string`, mergePolicy `Add`). Это
упрощает шаблон и снимает с пользователя необходимость поддерживать
словарь.

Этот эпизод полезен в тексте ВКР как пример осознанного отказа от
«красивой» онтологии в пользу ремонтопригодной (пример «эволюции
архитектурного решения»).

## 9. Черновой граф, редактирование и связь с онтологией

### 9.1. DraftGraph / DraftNode / DraftTriple

Описаны в `core/graph/draft_graph.py`. Это собственная промежуточная
структура поверх rdflib:

- `DraftNode` — узел с метаданными: `type` (IRI/LITERAL), `rdf_node`
  (URIRef/Literal или None), `error: Optional[str]` (если узла нет),
  `source: Optional[str]` (имя поля, из которого узел получен).
  `is_complete()` ⇔ `rdf_node is not None`.
- `DraftTriple` — `(subject, predicate, object)` плюс `triple_type`
  (TYPE / OBJECT_PROPERTY / DATA_PROPERTY).
- `DraftGraph` — список триплетов; `is_complete()` ⇔ все триплеты
  полные; `get_rdf_graph()` собирает чистый rdflib-Graph (только если
  все полные).

Зачем: чтобы донести до UI, **что именно не извлеклось**, и сохранить
ссылку на поле-источник.

Замечание: TemplateGraphBuilder и обёртки (DraftNode и тд.) намеренно
ограничевает DSL построения графа только необходимыми в предментной области 
возможностями, чтобы не работать напрямую с rdflib (лишние возможности
и путанница) и скрыть boilerplate код (например создание триплетов с :фамилия :имя 
и т.д. для каждой персоны).

### 9.2. EditedGraph — правки пользователя

Также в `draft_graph.py`. Двухслойная модель:

- `DraftGraph` (от builder) — read-only черновой граф. Перезаписывается при каждом
  прогоне шаблона;
- `EditedGraph(draft)` — журнал поправок:
  - `excluded_triple_indices: Set[int]` — какие триплеты исключить;
  - `node_overrides: Dict[(triple_index, role), DraftNode]` — какие
    узлы заменить.

`EditedGraph.build_modified_graph()` берёт исходный draft и
накатывает на него правки, собирая новый `DraftGraph`. Это и есть тот
граф, который уходит в коннектор.

Правки сериализуются отдельно (`draft_graph_edits.json`) — без
исходного графа. Это и означает «override-редактирование»: при
повторной обработке исходного документа правки **не теряются**,
если результат шаблона остался согласованным с ними; при изменении
шаблона/документа правки обнуляются (см. описание стадии GraphBuilder).

Кроме overrides поддерживаются **дополнительные факты** —
произвольный TTL-файл `supplementary_facts.ttl`, который коннектор
парсит и подмешивает к итоговому графу. Это отдушина для случаев,
когда шаблон в принципе не покрывает нужные знания, а добавить их в
граф всё равно надо.

### 9.3. Концептуальная схема «соотношение знаний»

Это полезный для текста ВКР образ. Множество «знания, реально
содержащиеся в документе», и множество «знания, попадающие в граф через
шаблон», частично пересекаются:

- знания **в обоих** — корректно извлечённое шаблоном;
- знания **только в документе** — не покрыто шаблоном (попадают в
  `supplementary_facts.ttl` или в overrides);
- знания **только из шаблона** — ложноположительные/устаревшие
  (исключаются через `excluded_triple_indices`).

Расчёт «90% правильно» — это собственная оценка, не по статистическим
тестам.

## 10. Онтология кафедры и политики слияния

Схема — `resources/onto/schema.ttl`. Namespace проекта —
`http://doc2onto.org/ontology#`. Префикс `:` в схеме указывает именно
на него; в коде он же — `SUBJECT_NAMESPACE_IRI` из `app/settings.py`.

### 10.1. Иерархия классов (важно для ВКР)

- `:Агент` — общий супер-класс, дальше:
  - `:Персона` (под-классы `:Студент`, `:Сотрудник`, **не дизъюнктны**:
    один человек может быть и студентом, и сотрудником);
  - `:Организация` (под-классы `:Университет`, `:СтруктурноеПодразделение`
    — `:Факультет`, `:Кафедра`, `:Лаборатория`; `:ВнешняяОрганизация`).
  - Дизъюнктность: `:Персона` и `:Организация` не пересекаются;
    подтипы `:Организация` дизъюнктны между собой.
- Образовательная структура: `:Группа`, `:НаправлениеПодготовки`,
  `:Профиль`.
- Академические активности: `:АкадемическаяАктивность` (родитель), под
  ней `:ВКР` и `:Практика`.
- Перечисления (named-individual enums): `:Должность`, `:УченаяСтепень`,
  `:УченоеЗвание`, `:Оценка`.

Принципы идентификации индивидов записаны в комментарии онтологии
(прямая цитата из `schema.ttl`):

> 1. Индивиды, чья текстовая идентификация неоднозначна (ФИО, названия
>    организаций, темы ВКР и т. п.), получают IRI в виде хеша от
>    нормализованной формы идентифицирующих признаков. Сами признаки
>    одновременно сохраняются как литеральные свойства индивида.
> 2. Индивиды с заведомо стабильным «техническим» идентификатором
>    (номер группы, код направления подготовки, учебный год, семестр)
>    хешированию не подвергаются — для них используется либо литерал,
>    либо IRI, безопасно построенный из самого идентификатора.
> 3. Перечисляемые типы (должность, учёная степень, учёное звание, вид
>    практики, итоговая оценка) выражены закрытыми списками именованных
>    индивидов с предсказуемыми IRI вида `:<Класс>_<Значение>` для
>    детерминированного маппинга из текста.

Принципы стабильности модели:

> - Документ — лишь источник фактов; знания не привязаны к документу
>   как к «центру».
> - Ограничения existential/cardinality на уровне TBox намеренно сведены
>   к минимуму: добавление новой частичной информации о существующем
>   индивиде не должно нарушать модель.
> - Соответствие классам выводится по `rdfs:domain` / `rdfs:range`
>   объектных и данных-свойств — это даёт мягкую типизацию и устойчивость
>   к неполным данным.

### 10.2. Политики слияния (mergePolicy)

Это **аннотация-свойство**, прикрепляемая к каждому property схемы:

| Политика | Поведение | Применяется к |
|---|---|---|
| `:Policy_Set` | single-valued, неизменное; полная замена `(s, p, *)` | идентифицирующие свойства, связи, смена которых = ошибка извлечения |
| `:Policy_SetByDate` | single-valued, временное; замена только если `effective_date` нового ≥ существующего | свойства состояния во времени (группа, тема ВКР) |
| `:Policy_Add` | multi-valued; чистый add | множественные свойства (телефоны, звания), `rdf:type` по умолчанию |

`effective_date` документа берётся коннектором по приоритетному списку
полей: `application_date`, `issue_date`, `protocol_date`,
`instruction_date`, `appointment_order_date`, `practice_start_date`,
`document_date`, `date`. Если ни одно не извлеклось — `None`. В
`Policy_SetByDate` факты без `effective_date` ведут себя как самые ранние
(могут быть «вытеснены» любым датированным).

### 10.3. Хранение онтологии

`OntologyRepository` (в `storage/`) хранит:

- **`schema.ttl`** — read-only TBox (резервная копия лежит и в
  `.data/ontology/`, и в `resources/onto/`).
- **`history.json`** — список добавленных документов (доджокумент-id,
  template-id, путь к фрагменту TTL, effective_date, время
  добавления).
- **`facts.jsonl`** — append-only журнал событий слияния (add /
  retract / reject) с полным контекстом. Производный индекс — можно
  пересобрать из истории.
- **`ontology.ttl`** — итоговая собранная модель (для просмотра).

Ключевое поведение: **переобработка документа** = удаление старой
записи из истории + повторное `merge_document(...)` с новым фрагментом,
с предварительным контролем целостности модели до изменений.

## 11. Подсистема LLM-взаимодействия

В системе 3 места, где вызывается LLM (все они используют
`app/agents.py:ask_gpt`):

1. **Извлечение полей из документа** (стадия Extractor, второй
   подэтап). Промпт: `extract_fields_sys.txt` + `extract_fields_user.txt`.
   На один документ — ровно один запрос. В payload — UDDM целиком +
   все поля шаблона.
2. **Генерация описания шаблона** по образцу документа.
   `generate_description_sys.txt` + `generate_description_user.txt`.
3. **Генерация кода шаблона** по описанию.
   `generate_template_code_sys.txt` (≈ 280 строк, перечислены все
   доступные импорты, концепты, idiom DSL, примеры) +
   `generate_template_code_user.txt`.

Конфигурация в `app/settings.py`: `DEFAULT_MODEL` (имя модели),
`DEFAULT_TIMEOUT_SECONDS` (60), `TEMPLATE_GENERATION_MAX_ATTEMPTS` (3 —
число итераций «генерация → валидация → доработка»).

Дополнительные особенности подсистемы:

- Все LLM-обращения логируются в отдельный файл `.data/logs/agents.log`
  (полный prompt + полный ответ + длительность).
- Контракт ответа экстрактора — **строгий JSON** с явно описанной
  комбинаторикой `status/value/error`. Системный промпт
  (`extract_fields_sys.txt`) перечисляет все 5 допустимых сценариев и
  отдельный «инвариант» внизу — это сделано после неудачных попыток
  получить стабильный JSON без жёстких правил.
- Кеширование запросов отсутствует. Запрос идёт каждый раз заново.
- Подсчёт токенов и cost-tracker отсутствуют. Это известное упрощение.
- Streaming-ответы не используются — берётся `output_text` из
  Responses API целиком.

## 12. Автоматизированная генерация шаблонов

Многошаговая процедура (создаётся в UI «Шаблоны»):

1. Пользователь подаёт на вход образец документа (один или несколько).
2. Генератор описания: LLM-агент видит UDDM-структуру образца и схему
   онтологии, формулирует краткое описание шаблона и таблицу полей 
   (что именно нужно извлекать) со столбами: | Название поля | Описание 
   | Где искать | Как извлекать | Маппинг в онтологию |.
3. Генератор кода: следующий вызов LLM-агента генерирует `code.py`. 
   Системный промпт содержит описание API (Field/Selector/Extractor/Normalizer, 
   концепты, builder), эталонный шаблон (`resources/template/code_example.py`) 
   и схему онтологии.
4. Финальный результат показывается пользователю; **ручная доводка**
   ожидается, особенно по части `classify` (LLM плохо угадывает
   характерные признаки документа без явных подсказок) и `build`
   (логика связывания индивидов).
5. Пользователь может запустить валидатор шаблона (`core/template/validation.py`),
   чтобы прогоняет шесть категорий проверок и собирает отчёт.

В тексте ВКР важно подчеркнуть: генерация шаблонов **не претендует на
полную автоматизацию**. Это инструмент ускорения, окончательный шаблон —
результат совместной работы автора и системы.

## 13. Пользовательский интерфейс

Главное окно (`ui/main_window.py:MainWindow`) содержит три боковые
вкладки.

### 13.1. Документы (`ui/documents/`)

Вкладка состоит из двух колонок:

- слева — список документов, фильтрация по статусу;
- справа — `DocView` с тремя суб-вкладками:
  - **Оригинал** (`original_tab.py`) — предпросмотр первой страницы
    PDF-конверсии, кнопка «Открыть оригинал в системной программе»;
  - **UDDM** (`uddm_tab.py`) — представление документа в формате UDDM
    (HTML и tree-view);
  - **Граф** (`graph_tab.py`) — двухпанельный редактор:
    - слева список узлов и троек (с подсветкой неполных и
      переопределённых);
    - справа форма редактирования выбранного элемента.
    Внизу — диалоги: «Источник факта» (показывает, из какого поля
    шаблона получился узел и кнопку «Открыть шаблон»),
    «Сгенерировать индивид» (выбор концепта + ввод значения).

Вверху страницы документа — статус-бар (показывает пройдённые стадии),
кнопка «Запустить/продолжить pipeline», кнопка «Сбросить и
переобработать» (доступные кнопки зависят от статуса).

### 13.2. Шаблоны (`ui/templates/`)

- список шаблонов;
- карточка шаблона с описанием, кнопками «Сгенерировать»
  (мульти-агентный flow), «Открыть в редакторе» (запускает внешнюю
  программу — VS Code, Notepad++ и т. п.), «Удалить»;
- HTML-подсветка кода (`python_code_html.py`), отчёт о валидации.

### 13.3. Онтология (`ui/ontology/ontology_tab.py`)

- слева иерархия классов и список индивидов;
- справа карточки `IndividualCardWidget` и `ClassCardWidget`:
  свойства, обратные ссылки, диалог «Источник факта» (из какого
  документа/шаблона пришёл триплет, со ссылкой обратно на документ).
- Поддерживаются ссылки между карточками (текст с link-стилем).

UI **синхронный**: тяжёлые операции (LLM-вызовы, генерация шаблона,
прогон pipeline на большом документе) подвешивают окно. Это известное
ограничение, прописано в разделе «Ограничения системы».

## 14. Что есть и чего намеренно нет

**Есть:**
- полный pipeline от файла до записи в онтологию;
- три суб-вкладки документа (оригинал/UDDM/граф) с навигацией;
- редактирование графа и сохранение правок;
- подсистема концептов с морфологией;
- LLM в экстракции и генерация шаблонов;
- структурная валидация шаблона с AST-анализом безопасности;
- журнал событий слияния (facts.jsonl).

**Чего намеренно нет:**
- **OCR / PDF-сканы** — каркас есть (внешние конвертеры, slot для OCR),
  но конкретных интеграций нет. PDF поддерживается только как
  «пере-конвертация в DOCX» через нормализатор `pdf_to_docx`, и
  сложные PDF-документы могут проходить с потерями.
- **Песочница исполнения шаблонов** — нет; защита только на уровне
  AST-анализа.
- **Многопользовательский режим / concurrent-доступ к онтологии** — нет;
  предполагается однопользовательское настольное приложение.
- **Пакетная обработка** — нет UI; каждый документ запускается
  отдельно. Сам pipeline воспроизводимый, технически возможна
  обвязка через скрипт.
- **Размеченный корпус и метрики качества** — нет. Оценка качества
  системы — качественная, по фиксированному набору документов.
- **Reasoner** — не используется. Согласованность модели проверяется
  «синтаксически» (домены/диапазоны свойств, классы); SROIQ-логика
  OWL не задействована.
- **Streaming-LLM, кеширование, токенный бюджет** — отсутствуют.

## 15. Ключевые принятые решения с обоснованиями (сводный список)

Каждый пункт содержит связку «проблема → решение → альтернативы».

1. **Разделение уровня данных и уровня знаний 
   `документ → UDDM → ABox аксиомы`.** Прямой переход
   смешивает форматную обработку и семантическую интерпретацию.
   Альтернативы: моноcистема, end-to-end LLM, готовые IDP-сервисы.
   Решение разделяет ответственность и делает шаблоны независимыми от
   формата.
2. **UDDM как минимально-достаточная модель.** Включены `text/p`,
   `list/item`, `table/row/cell`. Стили, секции, колонтитулы — нет.
   Альтернативы: хранить весь DOCX-объектный граф (привязка к формату),
   Markdown (теряет таблицы), Apache Tika XHTML / GROBID TEI
   (избыточно). Решение покрывает целевые документы и не усложняет
   шаблоны.
3. **Шаблон — Python-код, не DSL/YAML.** Полная выразительность,
   возможность смешивать структурный поиск и регулярки. Альтернативы:
   внешний DSL (как JAPE), декларативные YAML/JSON, code-as-data.
   Меры по снижению рисков: AST-валидация, ограниченные импорты,
   валидация выхода, разделение этапов.
4. **Поле шаблона как единица декларации значения.** Иначе шаблон
   превращается в непрозрачный набор операций.
5. **Fluent-DSL** Не даёт шаблону превратиться в произвольный код,
   избавляет от boilerplate кода.
6. **Концептно-ориентированная identity-модель.** Каждый класс
   онтологии получает свой `BaseConcept` с identity-стратегией.
   Идемпотентность парсинга — обязательное свойство.
7. **Композитные концепты для слабых сущностей.** ВКР = `hash(student)`,
   Практика = `hash(student | start_date)`. Иначе разные документы об
   одном студенте схлопывают разные практики.
8. **Гибридная экстракция «Детерминированный шаблон + LLM-уровень.** 
   Шаблонные правила извлечения гарантируют воспроизводимость
   и объяснимость, LLM закрывает «расхождения между почти одинаковыми 
   документами»
9.  **Override-редактируемый граф.** Двухслойная модель draft +
    edits хранит информацию о результате пайплайна и отдельно о
    ручных правках пользователя. 
10. **Дополнительные факты как TTL-файл.** Когда шаблон не покрывает
    знание, добавить можно вне шаблона.
11. **mergePolicy как аннотация на свойстве схемы.** Поведение слияния
    описано в TBox, а не в коде — это позволяет менять политики без
    кода. Альтернативы: «всегда Set» (теряет историю), «всегда Add»
    (засоряет модель устаревшими значениями).
12. **`effective_date` по приоритетному списку полей.** Безопаснее
    жёстко зафиксированной даты документа: если шаблон не извлёк
    основную дату, в дело идёт fallback.
13. **Валидация шаблона.** Исключает потенциально опасные и нерабочие
    шаблоны.
14. **Описание поля на естественном языке как часть DSL.** Это
    единственный текст, который видит LLM при fallback и при
    проверке корректности уже извлечённого значения.
15. **DraftNode хранит `error` и `source`.** Без них пользователь не
    мог бы понять, почему триплет неполный и из какого поля он
    собран; диагностика была бы поломана.
16. **Структурная валидация концептов в шаблоне.** Категория
    `ontology` сверяет обращения `ONTO.<имя>` со схемой — без неё
    опечатка в имени класса или свойства всплыла бы только на
    стадии `Connector`.

## 16. Терминология

- **UDDM** — *унифицированная модель представления документов*
  (Unified Document Data Model). НЕ «формат», а *модель*; формат
  сериализации — XML.
- **Класс документа** — это формализованное описание группы документов, 
  обладающих общей структурой и семантикой, для которых применяется 
  единый шаблон извлечения полей и построения RDF-триплетов
- **Шаблон** — это формализованное описание правил обработки класса документов, 
  определяющее классификацию документа, извлечение и нормализацию полей, 
  а также преобразование извлечённых данных в RDF-граф. 
  Программная модель шаблона включает в себя название (класс), описание
  и код шаблона.
- **Код шаблона** — Python-модуль с интерфейсом `BaseTemplateCode`.
  В нём указаны правила классификации, извлечения и построения графа.
- **Поле шаблона** — это именованная единица извлечения данных, 
  определяющая способ поиска, извлечения и нормализации значения в документе.
  НЕ «атрибут онтологии». Поле может представлять информацию о нескольких
  сущностях онтологии (например поле student_name = "Иванов Иван Иванович" 
  даёт iri студента и литералы - составляющие ФИО, из которых можно
  построить несколько онтологических фактов).
- **Концепт** — модуль, инкапсулирующий identity-стратегию для
  класса/типа онтологии. В OWL концептом также называют класс, поэтому
  для разделения ролей лучше называть концептом именно программную сущность,
  а классом онтологии именно сущность онтологии.
- **Политики слияния**: Set → «полная замена», SetByDate → «замена по
  дате», Add → «добавление».
- **DSL** — здесь имеется в виду внутренний fluent-API на Python, не
  внешний язык. Указывать «декларативный fluent-DSL внутри Python».
- **`effective_date`** — *эффективная дата документа*; не «дата
  создания» и не «дата документа» в общем смысле — это дата, к которой
  относятся факты документа.
- **«Гибридная экстракция»** — связка «DSL + LLM-проверка/коррекция».

## 17. Что было протестировано и что нет

Качественная апробация проводилась на следующем наборе реальных
документов (взятых от одного студента кафедры; имена обезличены при
описании):
- заявление на тему ВКР;
- заявление на практику (за два разных семестра);
- индивидуальное задание на практику;
- отчёт руководителя практики (отзыв);
- тезисы двух студенческих конференций.

Проверены сценарии:
- полный цикл от UPLOADED до ADDED_TO_MODEL;
- кросс-форматный тест (один документ в DOCX, DOC, PDF) — итоговый
  набор троек совпадает с точностью до нормализации;
- два почти одинаковых документа (оба заявления на практику, разные
  семестры) под одним шаблоном — в одном случае детерминированный путь
  справился полностью, в другом несколько полей были «вытянуты» только
  LLM-fallback’ом из-за сдвига в структуре;
- редактирование графа в UI: ручное создание/правка/удаление узлов и
  триплетов; сохранение правок; перезапуск pipeline без их потери (в
  пределах того, что шаблон не пересоздаёт draft).

Что **не** проверялось и не должно подаваться как достижение:
- статистические метрики (precision/recall/F1) на корпусе — нет
  размеченного корпуса;
- работа на сложных PDF-сканах через OCR;
- многопользовательская работа и concurrent merge в онтологию;
- обработка очень больших документов (сотни страниц);
- стабильность LLM-генерации шаблонов для типов документов, сильно
  отличающихся от уже виденных моделью.

Расширенная апробация на документах нескольких студентов запланирована
как развитие работы и в данной ВКР не проводится.

## 18. Ограничения системы и потенциал улучшений

1. Система реализована как десктопное приложение. Но архитектура системы
   создана так, чтобы отделить ядро шаблонов, логику приложения и UI.
   Поэтому при необходимости можно будет реализовать веб доступ.
2. Все данные сейчас хранятся локально (документы, шаблоны, логи, онтология).
   Всё это можно будет хранить в БД (в том числе онтологию в БД триплетов),
   но пока хранение сделано локально для упрощения. Работа с файлами реализована
   через специальные менеджеры, поэтому переделать на БД будет не сложно.
3. Поддерживаются только форматы doc, docx и pdf. Это основные форматы, но
   можно добавить больше конвертеров для большей универсальности системы.
