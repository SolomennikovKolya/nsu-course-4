# Презентация к защите ВКР — раскадровка

> **Цель**: ≤ 10 минут выступления + 5–10 минут вопросов.
>
> **Темп**: ~130 слов/мин = ~1300 слов всего.
>
> **Структура слайдов**: 12 слайдов, по 30–75 секунд на каждый.
>
> **Принципы оформления**:
> - на слайдах — минимум текста, максимум схем/таблиц;
> - всё, что говорится, не дублирует слайд буква в букву;
> - технические термины («UDDM», «концепт», «политика слияния»)
>   вводятся ровно один раз и потом используются свободно.

## Слайд 5 — Архитектурная концепция (≈ 60 сек)

**Что на слайде:** горизонтальная схема:

```
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────────┐
  │ Документ │ →  │   UDDM   │ →  │   Граф   │ →  │  Онтология   │
  │ (DOCX,   │    │ (унифи-  │    │  фактов  │    │   кафедры    │
  │  PDF, …) │    │  цир.)   │    │          │    │              │
  └──────────┘    └──────────┘    └──────────┘    └──────────────┘
     данные         данные          знания           знания
                    │                │
                    └─ форматная     └─ интерпретация по шаблону
                       обработка
```

Под схемой — три тезиса:
- *форматная независимость* шаблонов;
- *воспроизводимость* результата;
- *прозрачность* промежуточных шагов.

**Что говорить:**

> Ключевая архитектурная идея — отделить работу с форматом от
> работы со смыслом. Между документом и онтологией вводится
> промежуточный слой — унифицированное представление документа.
> Это иерархическое дерево, в котором сохраняются текст и
> минимально необходимая логическая структура: абзацы, списки и
> таблицы. На уровне унифицированного представления уже нет ни
> шрифтов, ни колонтитулов, ни различий между DOCX и PDF.
> Шаблоны извлечения пишутся раз и работают одинаково для всех
> поддерживаемых форматов. Это даёт три полезных свойства:
> форматную независимость, воспроизводимость результата и
> прозрачность для пользователя — на любой стадии видно, что
> система увидела в документе.

## Слайд 6 — Конвейер обработки (≈ 60 сек)

**Что на слайде:** пять блоков в горизонтальной цепочке с двумя строчками подписи в каждом:

```
 ┌─────────┐   ┌──────────┐   ┌────────────┐   ┌─────────┐   ┌──────────┐
 │ Конвер- │ → │ Класси-  │ → │ Экстрактор │ → │ Сборка  │ → │ Интегра- │
 │  тер    │   │ фикатор  │   │ DSL+LLM+   │   │ графа   │   │   ция    │
 │ → UDDM  │   │ → класс  │   │ нормализ.  │   │ фактов  │   │ в модель │
 └─────────┘   └──────────┘   └────────────┘   └─────────┘   └──────────┘
```

Внизу: *«состояние документа сохраняется после каждой стадии — конвейер возобновляем»*.

**Что говорить:**

> Обработка документа — конвейер из пяти стадий. Конвертер
> приводит исходный файл к унифицированному представлению.
> Классификатор по содержимому определяет, какому шаблону
> соответствует документ. Экстрактор извлекает значения полей —
> и это самый содержательный этап, к нему я ещё вернусь.
> Построитель графа из значений собирает черновой граф фактов в
> терминах онтологии. Коннектор сливает факты с общей моделью с
> учётом политик слияния. Состояние документа сохраняется после
> каждой стадии — если что-то прервалось, конвейер можно
> продолжить с того же места.

## Слайд 7 — Шаблоны и гибридная экстракция (≈ 75 сек)

**Что на слайде:** две колонки.

*Слева* — структура шаблона:

```
 ШАБЛОН
   ├── classify(doc)  — это «свой» документ?
   ├── fields()       — какие поля извлечь?
   └── build(b)       — как собрать факты?
```

*Справа* — три этапа экстрактора:

```
 1) ДЕТЕРМИНИРОВАННЫЙ ЭТАП
    селектор + извлекатель → «сырое» значение

 2) ЭТАП ЯЗЫКОВОЙ МОДЕЛИ
    подтвердить, исправить или найти заново

 3) НОРМАЛИЗАЦИЯ
    приведение к канонической форме через концепт
```

Внизу — тезис: *«детерминированная часть отвечает за воспроизводимость, языковая модель — за устойчивость к вариативности»*.

**Что говорить:**

> Шаблон — это программный модуль на Python с тремя обязательными
> методами: распознавание класса документа, описание извлекаемых
> полей и правила сборки графа. Каждое поле — это четвёрка:
> декларативный путь по дереву, цепочка строковых преобразований,
> правило нормализации и описание поля на естественном языке. Само
> извлечение значения идёт в три этапа. Сначала декларативные
> правила шаблона дают «сырое» значение. Затем языковая модель
> получает весь документ и все поля и либо подтверждает результат,
> либо исправляет его, либо находит то, что шаблон пропустил. И
> наконец нормализатор приводит значение к канонической форме.
> Главная мысль здесь — языковая модель не источник знаний, а
> *проверяющий механизм*. Основное извлекают правила; модель
> закрывает ровно те случаи, где они неточны. Это сохраняет
> воспроизводимость и одновременно даёт устойчивость к различиям в
> оформлении документов.

## Слайд 8 — Концепты и идентификация индивидов (≈ 60 сек)

**Что на слайде:** заголовок «Как один и тот же человек в разных
документах получает один и тот же IRI?», ниже — короткий пример:

```
 «направить Соломенникову Николаю Александровичу»
 «студент Соломенников Николай Александрович»
                    │
                    ▼  PersonConcept
        приведение к именительному (pymorphy3)
                    │
                    ▼
        ключ = «соломенников | н | а»
                    │
                    ▼
        IRI = Персона_<sha1(ключ)>     ← один и тот же
```

Справа таблица с четырьмя стратегиями идентификации:

```
 хеш от ФИО / названия       — Персона, Организация, Профиль
 стабильный идентификатор    — Группа (22204), Направление (09.03.01)
 именованный индивид         — Должность, Степень, Звание
 композитный                 — ВКР, Практика
```

**Что говорить:**

> Чтобы один и тот же человек или одна и та же организация в разных
> документах объединялись в один индивид онтологии, разработана
> концептно-ориентированная модель идентификации. Каждому классу
> онтологии — Персоне, Организации, Группе, ВКР и так далее —
> сопоставлен программный модуль, который умеет разобрать значение,
> привести его к канонической форме и вычислить идентификатор
> индивида. Для персон, например, ФИО морфологически приводится к
> именительному падежу, а ключ хеширования содержит фамилию и
> *инициалы* имени и отчества — это нужно, чтобы «полное имя» и
> «фамилия с инициалами» дали один и тот же идентификатор.
> Реализовано четыре стратегии идентификации, охватывающие все
> сущности кафедры — от учебных групп до композитных событий вроде
> практики, которая идентифицируется парой «студент + дата начала».

## Слайд 9 — Граф фактов и интеграция в модель (≈ 60 сек)

**Что на слайде:** две концептуальные схемы.

*Слева* — двухслойная модель редактирования:

```
   ┌──────────────────┐         ┌──────────────────┐
   │  Черновой граф   │   +     │  Слой правок     │
   │  (от шаблона)    │         │  пользователя    │
   └──────────────────┘         └──────────────────┘
            ↓                            ↓
         автоматически                 ручное
                ↘  ↙
         ┌──────────────────┐
         │  Итоговый граф   │  → онтология
         └──────────────────┘
```

*Справа* — три политики слияния (как аннотации на свойствах схемы):

```
 :Policy_Set       — полная замена   (:фамилия, :авторВКР)
 :Policy_SetByDate — замена по дате  (:обучаетсяВГруппе, :темаВКР)
 :Policy_Add       — добавление      (:телефон, :учёноеЗвание)
```

**Что говорить:**

> Черновой граф фактов, который собирает шаблон, неизменяемый, но
> пользователь может его править. Правки хранятся отдельным слоем:
> при пересборке черновика правки сохраняются и автоматически
> применяются заново. Это снимает противоречие между автоматической
> повторяемостью и возможностью ручного вмешательства. Слияние
> документа с общей моделью устроено так: для каждого свойства
> схемы в самой онтологии задана политика слияния — полная замена,
> замена по дате или добавление. Это позволяет менять поведение
> слияния без правки программы. Дополнительно ведётся журнал событий
> слияния и история документов; вся ABox-часть онтологии — это
> производное от истории, что делает откат документа тривиальной
> операцией: удалить запись из истории и пересобрать.

## Слайд 10 — Реализация и интерфейс (≈ 60 сек)

**Что на слайде:** скриншот вкладки документа с редактором графа
(можно показать неполный узел с выделением цветом). По бокам — три
короткие подписи:

- *Стек*: Python 3.11, PySide6, rdflib, pymorphy3, OpenAI SDK (gpt-5.4-mini)
- *Структура UI*: Документы / Шаблоны / Онтология
- *Возможности редактора графа*:
  - подсветка неполных и переопределённых узлов;
  - генерация значения через концепт с предпросмотром IRI;
  - сброс правок отдельных узлов;
  - переходы «факт → документ-источник», «индивид ↔ класс».

**Что говорить:**

> Система реализована на Python с графическим интерфейсом на
> PySide6. Работа с RDF — через rdflib, морфология — pymorphy3,
> языковая модель — gpt-5.4-mini через OpenAI SDK. Интерфейс
> устроен как три вкладки: документы, шаблоны и онтология.
> Особенно подчеркну редактор графа фактов на слайде. Если шаблон
> что-то не извлёк, неполные узлы подсвечиваются цветом и
> показывают, какое поле стало источником проблемы. Прямо в
> интерфейсе можно создать индивид через выбор концепта,
> предварительно увидев, какой получится IRI. Каждый факт можно
> проследить до конкретного документа-источника, а в карточке
> индивида работают переходы между связанными сущностями.


*Справа* — проверенные сценарии:

```
 ПРОВЕРЕНО
   ✓ полный цикл от файла до онтологии
   ✓ кросс-форматный тест: DOCX, DOC, PDF → один результат
   ✓ два похожих документа под одним шаблоном:
       LLM-коррекция компенсирует сдвиг структуры
   ✓ ручное редактирование графа в интерфейсе
```

**Что говорить:**

> Качественная апробация проводилась на наборе реальных документов
> кафедры одного студента — всего семь документов разных типов.
> Все документы прошли конвейер до записи фактов в общую модель;

## Возможные вопросы и заготовки ответов

Стандартные вопросы при защите. Заранее подготовленные ответы
помогают отвечать кратко и по делу.

**1. Почему именно Python для шаблонов? Не выйдут ли шаблоны
небезопасными?**

> Python выбран потому, что он одновременно язык приложения и язык
> шаблонов — это устраняет необходимость в собственном DSL.
> Безопасность обеспечивается статическим анализом исходного кода
> шаблона по шести категориям: запрещённые импорты, опасные
> вызовы, обход sandbox через магические атрибуты, корректность
> полей, корректность сборки графа, согласованность с онтологией.
> При этом честно отмечу, что полноценной программной песочницы
> нет — это компромисс с учётом доверенного окружения кафедры и
> направление дальнейшего развития.

**2. Что произойдёт, если языковая модель ошибётся?**

> Языковая модель в системе не первичный источник знаний, а
> проверяющий механизм. Если она предложит неверное значение, его
> отвергнет нормализатор поля — например, если LLM сгенерирует
> «дата заявления = 32 декабря», `DateConcept` это не разберёт. А
> если значение пройдёт нормализатор и при этом неверно
> семантически, его можно поправить в редакторе графа: правка
> сохранится и переживёт повторную обработку. Дополнительно ведётся
> журнал всех обращений к модели, что позволяет восстановить
> контекст каждого её решения.

**3. Почему отказались от концепта «вид практики»?**

> Изначально вид практики был перечислением с закрытым списком:
> учебная, производственная, НИР, преддипломная. На практике
> реальные документы постоянно использовали формулировки вроде
> «производственной практики (научно-исследовательской работы)» в
> родительном падеже, которые не сопоставлялись с
> нормализованными синонимами. Поддержка словаря синонимов
> оказалась непропорционально трудоёмкой. Принято решение
> отказаться от закрытого словаря — вид практики хранится как
> свободная строка. Это иллюстрация принципа «ремонтопригодность
> важнее формальной красоты».

**4. Как обеспечивается воспроизводимость, если в конвейере есть
LLM?**

> Воспроизводимость детерминированной части — полная: одни и те
> же входные данные всегда дают один и тот же результат.
> Языковая модель — единственный недетерминированный компонент, и
> её результат сохраняется в истории извлечения каждого поля.
> На практике для одного и того же документа модель в большинстве
> случаев даёт согласованные ответы, поскольку контракт ответа
> жёстко формализован пятью сценариями исхода с явными
> инвариантами. Полная воспроизводимость через детерминированный
> сэмплинг — известная возможность OpenAI API и может быть
> включена при необходимости.

**5. Чем разработка отличается от Apache Tika и GROBID?**

> Apache Tika возвращает плоский текст без структуры; GROBID
> работает только с научными PDF и возвращает результат в стандарте
> TEI без привязки к конкретной онтологии. Разработанная система
> сразу строит факты в терминах фиксированной онтологической
> модели кафедры, поддерживает три формата документов (DOC, DOCX,
> PDF), включает гибридную экстракцию с языковой моделью, ручное
> редактирование результата и отслеживание происхождения каждого
> факта. То есть это не альтернатива Tika и GROBID, а решение
> другой задачи — пополнения конкретной онтологии, для которой
> универсальные инструменты не подходят.

**6. Сколько примерно времени занимает обработка одного документа?**

> Конкретное время определяется в основном задержкой обращения к
> языковой модели. Детерминированные стадии (преобразование,
> классификация, нормализация, сборка графа, интеграция в модель)
> отрабатывают за доли секунды. Один запрос к языковой модели —
> около 5–15 секунд в зависимости от объёма документа. То есть
> типичный документ объёмом до десяти страниц обрабатывается
> примерно за 10–20 секунд. Это приемлемо для интерактивной
> работы; пакетный режим в текущей версии не реализован.

**7. Что произойдёт, если в общей модели уже есть индивид с теми
же ФИО, но это другой человек?**

> Это известный риск стратегии «хеш от ФИО». Реализованы две меры.
> Во-первых, согласование IRI выполняется консервативно: при
> множественности кандидатов автоматическое объединение
> блокируется. Во-вторых, ключ хеширования содержит фамилию и
> инициалы имени и отчества — вероятность коллизии в пределах
> кафедры крайне мала, но не нулевая. Если коллизия всё же
> произойдёт, она будет видна в карточке индивида (там окажутся
> разные варианты ФИО) и может быть разрешена через ручное
> редактирование графа или откат документа.
