# ГЛАВА 3. Реализация и апробация системы

На этапе реализации архитектурные решения, разработанные в
предыдущей главе, преобразуются в работающий программный код. В
настоящей главе рассматриваются ключевые технические аспекты этого
преобразования: выбор технологического стека и его обоснование,
особенности реализации модулей конвейера обработки документа,
устройство подсистемы взаимодействия с большой языковой моделью,
организация средств автоматизированной генерации шаблонов,
устройство хранилища и репозитория онтологии, организация
графического интерфейса, а также результаты апробации системы на
реальных документах кафедры. Завершает главу обсуждение известных
ограничений системы и направлений её дальнейшего развития.

В отличие от предыдущей главы, в которой рассматривались
концептуальные и архитектурные решения, настоящая глава
сосредотачивается на конкретных технических деталях их воплощения.
При этом сознательно избегается повторение архитектурных
обоснований: каждое описанное здесь решение реализации опирается на
концептуальный фундамент, заложенный в главе 2.

## 3.1 Технологический стек

Реализация системы выполнена на языке программирования общего
назначения с использованием набора зрелых открытых библиотек. Выбор
конкретных технологических решений для каждой подсистемы
обусловлен сочетанием функциональных возможностей библиотек,
качества их документации и поддержки, а также соответствия общему
характеру проекта.

В качестве основного языка реализации выбран **Python** версии 3.11
\[?\]. Выбор обоснован зрелой экосистемой библиотек обработки
данных, наличием готовых средств работы с RDF и онтологиями,
кросс-платформенностью реализации и относительной простотой
представления шаблонов извлечения как пользовательского кода.
Поскольку шаблоны в системе являются программными модулями (см.
раздел 2.4), выбор широко распространённого языка программирования
существенно снижает порог входа для авторов шаблонов.

Графический интерфейс реализован на основе библиотеки **PySide6** —
официальной привязки кросс-платформенной библиотеки виджетов Qt
версии 6 к языку Python \[?\]. Библиотека обеспечивает зрелую
модель виджетов, поддержку стилевого оформления, встроенные
инструменты отображения HTML и PDF, а также механизмы обработки
событий, удобные для построения многооконных интерактивных
приложений. Кросс-платформенность Qt позволяет одной и той же
кодовой базе работать в основных операционных системах без
существенных изменений.

Работа с RDF-графами и онтологическими моделями выполняется
посредством библиотеки **rdflib** \[?\]. Библиотека реализует
полный набор стандартных операций над RDF-графами: загрузку и
сохранение в основных форматах сериализации (Turtle, RDF/XML,
JSON-LD), стандартные пространства имён (RDF, RDFS, OWL, XSD,
FOAF и другие), операции с триплетами и индивидами. В рамках
системы rdflib используется как внутреннее представление
итогового графа, передаваемого на интеграцию с общей моделью
кафедры.

Для разбора документов в формате DOCX применяется собственный
разборщик внутренней структуры документа на основе стандартной
библиотеки разбора XML языка Python; в качестве вспомогательного
инструмента доступа к содержимому архива используется
стандартная библиотека работы с ZIP-архивами. Преобразование
документов из формата DOC в формат DOCX выполняется через
обращение к внешним программным средствам — пакету LibreOffice в
неинтерактивном режиме либо к Microsoft Word через
COM-интерфейс — с реализацией цепочки последовательных попыток.
Преобразование PDF к DOCX выполняется через сторонний сервис
конвертации.

Для морфологической обработки русского языка — приведения частей
ФИО к именительному падежу при формировании идентификаторов
индивидов — применяется библиотека **pymorphy3** \[?\]. Она
обеспечивает разбор слов с указанием грамматических признаков
(падеж, число, род), что необходимо для надёжного восстановления
именительной формы из произвольного падежа.

Взаимодействие с большой языковой моделью реализовано через
официальный программный интерфейс компании-поставщика модели; имя
конкретной используемой модели задаётся в настройках приложения
как константа, что позволяет при необходимости заменить модель без
изменения программного кода.

Прочие используемые библиотеки относятся к категории
вспомогательных и применяются в строго определённых местах:
проверка типов структур данных, обработка переменных окружения,
рендеринг HTML и подсветка синтаксиса в графическом интерфейсе. Их
выбор не оказывает существенного влияния на архитектуру системы и
не требует отдельного обсуждения.

## 3.2 Реализация конвейера обработки документа

### 3.2.1 Управление состоянием документа и возобновляемостью

Состояние обработки каждого документа в системе явно представлено в
виде последовательного перечисления, элементы которого
соответствуют шести стадиям прохождения конвейера: документ
загружен в систему; построено унифицированное представление;
определён класс документа; извлечены и нормализованы значения
полей; построен черновой граф фактов; факты добавлены в общую
модель. Каждая стадия конвейера переводит документ из одного
состояния в следующее, что обеспечивает свойство возобновляемости,
обоснованное в разделе 2.3.

Состояние обработки является частью метаданных документа, которые
сохраняются вместе с самим документом в персистентном хранилище.
Это позволяет приложению при перезапуске восстанавливать полное
состояние всех ранее загруженных документов и продолжать их
обработку с того места, на котором она была остановлена. Для
вычисления порядка состояний реализовано целочисленное
представление перечисления, по которому выполняется сравнение
текущего состояния с целевым.

Поскольку различные стадии конвейера оперируют разнородными по
объёму данными (некоторые из которых, такие как текст
унифицированного представления крупного документа, могут занимать
существенный объём памяти), для оптимизации работы с этими данными
введён *контекст документа* — рабочая обёртка, обеспечивающая
ленивую загрузку данных по требованию. При первом обращении к
данным они загружаются из соответствующего файла; при последующих
обращениях — берутся из локального кэша; по выходу из обработки
ресурсы освобождаются. Такое решение исключает необходимость явной
передачи больших объектов через все уровни вызовов и позволяет
обрабатывать документы независимо друг от друга без накопления
данных в оперативной памяти.

### 3.2.2 Реализация преобразования к унифицированному представлению

Реализация первой стадии конвейера организована как реестр трёх
типов преобразований, описанных в разделе 2.3.2: нормализующих
преобразований между форматами без потерь, внутренних разборщиков
структуры документов и каркаса для подключения внешних
извлекателей данных.

Внутренний разборщик документов формата DOCX реализован в виде
собственного парсера, обходящего внутреннюю XML-структуру
документа. Документ DOCX представляет собой ZIP-архив,
содержащий описание содержимого в виде XML-файла, в котором
каждый абзац представлен отдельным элементом со своими
характеристиками оформления. Разборщик распознаёт и преобразует в
элементы унифицированного представления следующие конструкции
исходного документа:

- *обычные абзацы* — преобразуются в параграфы унифицированного
  представления; пустые абзацы пропускаются;
- *элементы нумерованных и маркированных списков* —
  опознаются по наличию у абзаца специальной разметки нумерации;
  с учётом уровня вложенности группируются в иерархические
  списки;
- *таблицы* — обходятся рекурсивно; в каждой ячейке таблицы
  допускается произвольное содержимое (включая вложенные
  таблицы);
- *заголовки разделов* — опознаются по имени стиля абзаца,
  начинающемуся с известных префиксов; в случае нераспознанного
  стиля применяется эвристика, опирающаяся на сочетание признаков
  «короткая длина текста + жирное начертание + центрированное
  выравнивание».

Заголовки разделов служат границами между текстовыми блоками
унифицированного представления: смена заголовка завершает
накопление параграфов в текущем текстовом блоке и начинает
новый. Это позволяет разбить сплошной текст документа на
логически связные единицы, удобные для последующего шаблонного
анализа.

Преобразование документов из формата DOC в формат DOCX и из формата
PDF в формат DOCX реализовано через обращение к внешним
программным средствам. Для документов формата DOC применяется
пакет LibreOffice в неинтерактивном режиме либо, при его
отсутствии, Microsoft Word через COM-интерфейс. Для документов
PDF используется сторонний сервис конвертации. Все
преобразования формата применяются рекурсивно до тех пор, пока
формат документа не стабилизируется, после чего управление
передаётся внутреннему разборщику.

После завершения построения унифицированного представления оно
проверяется на соответствие XSD-схеме. Документы, не прошедшие
проверку, дальше по конвейеру не передаются, что обеспечивает
раннее обнаружение ошибок преобразования.

### 3.2.3 Реализация классификатора и экстрактора

Реализация классификатора (вторая стадия) сознательно проста.
Список доступных шаблонов получается через менеджер шаблонов,
после чего у каждого из них последовательно вызывается метод
определения принадлежности документа классу. В качестве результата
возвращается первый шаблон, давший положительный ответ. При
неудаче автоматической классификации соответствующий статус
документа сохраняется, и пользователь получает возможность
указать класс вручную через графический интерфейс.

Реализация экстрактора (третья стадия) разделена на три
последовательно вызываемых внутренних метода, соответствующих
трём этапам гибридной экстракции, описанным в разделе 2.3.4:
декларативное извлечение, проверка и коррекция языковой моделью,
нормализация. Каждый из методов оперирует общей структурой
данных — *результатом извлечения*, в которой по каждому полю
сохраняются значения и причины ошибок всех трёх этапов.

Декларативное извлечение для каждого поля шаблона запускает
объявленные в составе поля селектор и извлекатель и сохраняет
результат либо причину отказа. Этап коррекции языковой моделью
выполняет один запрос к модели, передавая в него унифицированное
представление документа целиком, список полей шаблона и
результаты декларативного этапа; ответ модели разбирается по
строгому контракту и сохраняется в результате извлечения. Этап
нормализации для каждого поля пропускает «сырое» значение (с
приоритетом результата языковой модели) через нормализатор,
сохраняя каноническое значение либо причину отказа в нормализации.

Структура результата извлечения сохраняется в персистентном
хранилище после завершения третьей стадии. Это обеспечивает
прозрачность процесса для пользователя: для каждого поля можно
установить, кем именно (декларативным этапом, языковой моделью)
было получено значение, и по какой причине отдельные поля
оказались не извлечены или не нормализованы. Эти сведения
отображаются в графическом интерфейсе и активно используются при
отладке шаблонов.

### 3.2.4 Реализация построителя графа фактов

Реализация четвёртой стадии конвейера — построения чернового графа
— основана на ключевом архитектурном решении, обсуждённом в
разделе 2.3.5: построитель никогда не выбрасывает исключений; любая
ошибка построения превращается в *неполный узел* графа с
поясняющим сообщением и ссылкой на исходное поле.

Перед вызовом правил сборки шаблона для каждого объявленного поля
из результата извлечения извлекается каноническое значение (или
сохраняется отметка об отсутствии значения). Сформированный
словарь канонических значений передаётся в построитель графа,
после чего вызывается метод сборки шаблона. Все обращения шаблона
к построителю транслируются в добавление триплетов в накапливаемый
черновой граф; обращения к отсутствующим или некорректным
значениям полей превращаются в неполные узлы.

Также предусмотрена обработка непредвиденных ошибок,
возникающих в коде самого шаблона. Если при выполнении правил
сборки возникает исключение (не связанное с типовыми ошибками
извлечения, обрабатываемыми построителем), частично построенный
граф сохраняется в обычном виде, а отдельным файлом записывается
структурированный отчёт об ошибке: тип исключения, его сообщение,
полная трассировка стека, идентификатор и название шаблона,
сводная статистика по полям и триплетам на момент возникновения
ошибки. Этот отчёт служит инструментом разработчика шаблона,
позволяющим быстро локализовать причину сбоя.

Реализация диагностики после успешной сборки также заслуживает
упоминания. По завершении вызова правил сборки журналу
выдаётся сводная статистика по построенному графу: общее число
триплетов, число полных и неполных, распределение по типам
триплетов (типизация индивидов, объектные свойства, свойства
данных). При наличии неполных триплетов отдельно перечисляются
поля-источники неполных узлов с указанием числа таких узлов; это
наглядно показывает, какое именно поле документа стало основной
причиной неполноты графа.

### 3.2.5 Реализация интеграции в общую модель

Реализация пятой стадии (коннектор) выполняет последовательность
действий, описанную в разделе 2.3.6. Сначала к черновому графу
применяются ручные правки пользователя (исключаемые триплеты и
переопределения узлов); затем подмешиваются дополнительные факты
из самостоятельного TTL-файла; затем выполняется опциональное
согласование идентификаторов с уже существующими в общей модели
индивидами; затем определяется эффективная дата документа по
приоритетному списку полей дат; наконец, выполняется собственно
слияние с общей моделью.

Вычисление эффективной даты заслуживает отдельного описания.
Реализация перебирает фиксированный приоритетный список имён
полей дат (дата подачи заявления, дата выдачи задания, дата
протокола, дата приказа, дата начала практики, дата документа); для
каждого имени проверяется наличие соответствующего поля в
результате извлечения; первое найденное значение разбирается как
дата и при успехе принимается за эффективную дату документа. Для
разбора поддерживаются основные форматы записи дат, принятые в
русскоязычных документах: ISO-формат, числовой с разделителями,
запись с месяцем словом в любом падеже. Учтены также распространённые
особенности оформления — кавычки вокруг числа дня, добавление
сокращения «г.» или «г.» в конце записи.

Перед слиянием выполняется проверка целостности текущей модели. В
случае обнаружения нарушений целостности (например, наличия в
модели нескольких значений у предиката с политикой полной замены)
интеграция блокируется до устранения проблемы. Это решение
позволяет немедленно выявлять накопленные нарушения и не допускать
их распространения.

## 3.3 Подсистема взаимодействия с языковой моделью

### 3.3.1 Точки применения

Обращения к большой языковой модели в системе выполняются в трёх
строго определённых местах. Первое — этап проверки и коррекции
значений полей в составе экстрактора (см. раздел 2.3.4): один
запрос на документ, в котором передаётся унифицированное
представление документа и полный список полей шаблона. Второе и
третье — этапы автоматизированной генерации шаблонов (см. раздел
3.4): отдельные запросы на формирование описания шаблона по
образцу документа и на генерацию исполняемого кода шаблона по
описанию.

Все обращения к языковой модели реализованы через единую точку —
функцию обращения к модели, инкапсулирующую установление
соединения с программным интерфейсом поставщика, передачу
системного и пользовательского промптов, обработку ответа,
журналирование запроса и ответа. Это обеспечивает единообразие
всех обращений и облегчает их аудит.

### 3.3.2 Структура промптов и контракт ответа

Все промпты, используемые в системе, вынесены в отдельные текстовые
файлы и загружаются в момент обращения. Для каждой точки применения
поддерживаются два файла — *системный промпт*, описывающий роль
модели и общие требования к ответу, и *пользовательский промпт*,
содержащий конкретный вход для текущего обращения. Использование
шаблонной подстановки позволяет передавать в промпт произвольные
структурированные данные (унифицированное представление документа,
список полей, схему онтологии).

Контракт ответа для основной точки применения — извлечения значений
полей — оформлен с особой строгостью. Системный промпт
формулирует требования к языковой модели в виде явно перечисленных
сценариев исхода, на каждый из которых наложены инварианты,
исключающие неоднозначные комбинации. Для каждого поля модель
обязана выдать ответ, соответствующий ровно одному из пяти
сценариев:

1. Значение, извлечённое декларативным этапом, корректно и
   изменений не требует.
2. Значение присутствует, но некорректно; правильное значение
   найдено в документе.
3. Значение присутствует, но некорректно; правильное найти не
   удалось.
4. Значение отсутствует; в документе найдено корректное значение.
5. Значение отсутствует и не найдено.

На комбинации значений в ответе наложены явные инварианты:
например, при подтверждении ранее извлечённого значения поле
с новым значением должно быть пустым, что специально оговаривается
для исключения двусмысленных интерпретаций. Подобная детальная
формализация контракта ответа выработана опытным путём после
неудачных попыток получить стабильный структурированный ответ при
менее жёстких требованиях. Опыт реализации показал, что качество
ответа модели в задачах структурированного извлечения определяется
не столько собственно её способностями, сколько детальностью
контракта, заданного в системном промпте.

### 3.3.3 Журналирование обращений

Все обращения к языковой модели сохраняются в отдельный
тематический журнал — файл, существующий параллельно с основным
журналом приложения. Для каждого обращения в журнал записываются:
момент времени начала обращения; имя использованной модели; полный
текст системного промпта; полный текст пользовательского промпта;
полный текст ответа модели; длительность обращения. В случае
ошибки на стороне поставщика модели в журнал записывается тип и
текст возникшего исключения.

Подобный режим журналирования делает все обращения к языковой
модели полностью прослеживаемыми. По журналу в любой момент можно
восстановить контекст конкретного решения системы и при
необходимости воспроизвести обращение. Это особенно ценно в
условиях, когда поведение модели может меняться от обращения к
обращению.

### 3.3.4 Осознанные упрощения

В текущей реализации сознательно отсутствует ряд возможностей,
которые могли бы быть полезны в продуктивной эксплуатации, но не
требуются в условиях исследовательской работы.

Во-первых, отсутствует *кэширование запросов*: одинаковые
обращения к модели не объединяются и каждый раз приводят к новому
вызову. В пилотных сценариях работы число обращений невелико, и
введение кэширования не принесло бы заметной экономии.

Во-вторых, отсутствует *учёт стоимости и потребления токенов*:
расход на обращения к модели не суммируется и не контролируется
программно. В условиях исследовательской работы расходы
отслеживаются вручную через интерфейс поставщика.

В-третьих, не используется *потоковая выдача ответа* — ответ
модели берётся целиком после завершения генерации. Поскольку
результат используется атомарно (в виде завершённого
структурированного объекта), потоковая обработка не дала бы
функционального выигрыша.

Перечисленные упрощения являются осознанными и при необходимости
могут быть устранены при переходе системы к продуктивной
эксплуатации.

## 3.4 Автоматизированная генерация шаблонов

### 3.4.1 Многошаговая процедура

Поскольку разработка шаблонов остаётся единственным этапом
эксплуатации системы, не поддающимся полной автоматизации, в
систему встроен механизм помощи пользователю по созданию заготовок
шаблонов на основе образцов документов. Процедура состоит из
последовательности шагов, выполняемых через графический интерфейс.

На первом шаге пользователь подаёт на вход образец документа
интересующего класса. После загрузки документа выполняется его
преобразование к унифицированному представлению — для генерации
шаблона важна именно структура документа, как она будет видна
шаблону при последующей обработке.

На втором шаге выполняется обращение к языковой модели для
*генерации описания шаблона*. Системный промпт инструктирует
модель сформировать краткое описание класса документа и таблицу
полей, которые предлагается извлекать. Каждая строка таблицы
содержит имя поля (в строго заданном формате
snake_case), смысловое описание, указание места поиска поля в
документе, правило извлечения значения и предполагаемое
отображение поля на термины онтологии. В пользовательский промпт
передаётся унифицированное представление образца документа и
полная схема онтологии, доступной системе.

На третьем шаге выполняется обращение к языковой модели для
*генерации исполняемого кода шаблона* по полученному описанию.
Системный промпт содержит детальное описание программного
интерфейса для написания шаблона: контракт класса шаблона с
тремя обязательными методами, доступные операции декларативного
языка извлечения полей (селектор, извлекатель, нормализатор),
полный перечень концептов с указанием их назначения и стратегии
идентификации, типовые паттерны построения графа для разных
классов документов. Также прилагается эталонный пример пустого
шаблона. В пользовательский промпт передаются: название шаблона,
сгенерированное на предыдущем шаге описание, унифицированное
представление образца документа и схема онтологии.

На четвёртом шаге результат генерации передаётся пользователю для
*ручной доработки*. Окончательное оформление шаблона, в особенности
правил распознавания принадлежности документа классу и
нетривиальной логики связывания фактов в графе, возлагается на
автора. Пользователь имеет возможность открыть код сгенерированного
шаблона во внешнем редакторе и редактировать его обычными
средствами разработки.

На завершающем шаге, перед использованием шаблона в обработке,
запускается его структурная валидация (см. раздел 3.4.2),
формирующая отчёт о выявленных проблемах.

В дипломной работе сознательно подчёркивается, что
автоматизированная генерация шаблонов *не претендует на полную
автоматизацию*. Это инструмент ускорения работы автора шаблона,
позволяющий за короткое время получить работающую заготовку, в
которую затем вносятся уточнения. Опыт использования системы
показывает, что наиболее существенной ручной правке подвергаются
правила классификации документа (языковая модель плохо угадывает
характерные признаки документа без явных подсказок) и логика
связывания фактов в графе (требующая глубокого понимания
предметной области и онтологической модели).

### 3.4.2 Структурная валидация шаблона

Структурная валидация шаблона реализована в виде программного
модуля, последовательно выполняющего проверки по шести категориям
и формирующего сводный отчёт. Каждое замечание отчёта имеет
указание категории, уровня важности (ошибка или предупреждение),
текста сообщения и при необходимости — детального пояснения с
точной локализацией в исходном коде. Шаблон считается прошедшим
валидацию при отсутствии замечаний уровня «ошибка».

*Категория структурной корректности* проверяет, что шаблон
реализует все требуемые методы фиксированного интерфейса и сам
интерфейс не остаётся абстрактным. Эта проверка выполняется через
прямое обращение к свойствам класса шаблона.

*Категория безопасности* реализована через анализ абстрактного
синтаксического дерева исходного кода шаблона. По дереву ищутся
конструкции импорта, обращения к опасным встроенным функциям и
обращения к опасным магическим атрибутам. Списки разрешённых
модулей для импорта, запрещённых модулей с указанием конкретной
угрозы (доступ к файловой системе, запуск подпроцессов, сетевые
соединения и т. п.), запрещённых встроенных функций и магических
атрибутов поддерживаются в виде явных перечислений. Импорты
модулей, не входящих в список разрешённых, фиксируются как
предупреждения; импорты заведомо опасных модулей и обращения к
запрещённым конструкциям — также как предупреждения, но с явным
указанием угрозы.

*Категория корректности списка полей* проверяет результат вызова
соответствующего метода шаблона: тип возвращаемого значения,
непустоту списка, корректность типа каждого элемента,
соответствие имён полей формату snake_case, отсутствие
дубликатов имён, наличие непустых смысловых описаний, корректность
типов селектора, извлекателя и нормализатора.

*Категория проверки распознавания класса* выполняет пробный вызов
соответствующего метода шаблона с тестовыми параметрами (пустое
имя файла, пустое унифицированное представление). Главная цель
этой проверки — убедиться в отсутствии падения метода в
тривиальных условиях.

*Категория сухого прогона сборки графа* выполняет пробное
построение графа с синтетическими значениями всех объявленных
полей. Набор синтетических значений подобран по подсказкам в
именах полей: имя, содержащее упоминание ФИО, получает заведомо
парсящееся ФИО; имя, содержащее упоминание даты, получает
ISO-форму даты; и так далее для всех типичных видов полей.
Это позволяет убедиться, что код сборки графа корректно
обрабатывает значения, проходящие через типовые нормализаторы.

*Категория согласованности с онтологией* выполняет анализ
обращений к терминам онтологии в коде шаблона. По синтаксическому
дереву извлекаются все обращения к именам терминов, после чего
сверяются с фактическим перечнем терминов, объявленных в схеме
онтологии. При обнаружении несовпадения в отчёт добавляется
предупреждение; при возможности подсказывается ближайшее по
написанию имя из числа фактически имеющихся в схеме, что облегчает
обнаружение опечаток.

### 3.4.3 Безопасность пользовательского кода

Принципиально важный аспект работы с шаблонами в виде
исполняемого кода — обеспечение безопасности их выполнения.
В системе принят подход, описанный в разделе 2.4.3: безопасность
обеспечивается совокупностью статического анализа исходного кода и
ограничений на состав допустимых импортов, без применения
отдельной программной песочницы исполнения.

Принятый подход является сознательным компромиссом, основанным на
оценке практических рисков. Полноценная программная песочница для
исполнения произвольного кода Python представляет собой нетривиальную
техническую задачу, не имеющую универсального стандартного
решения. В то же время работа кафедры предполагает доверенное
окружение, в котором шаблоны разрабатываются ограниченным кругом
авторов и проходят проверку перед использованием. В этих условиях
уровень защиты, обеспечиваемый статическим анализом, признан
достаточным.

Введение полноценной программной песочницы рассматривается как
направление дальнейшего развития, целесообразное при переходе
системы к режиму, в котором шаблоны могут разрабатываться менее
доверенными участниками.

## 3.5 Хранилище данных и репозиторий онтологии

Все данные системы хранятся в локальной файловой системе,
организованной по описанной в разделе 2.8.4 схеме. Документы,
шаблоны и онтологическая модель размещены в раздельных подкаталогах
с собственной структурой; для каждого документа создаётся отдельный
подкаталог, в который сохраняются исходный файл, унифицированное
представление, обратные представления для просмотра, результат
извлечения полей, черновой граф, слой пользовательских правок,
дополнительные факты, итоговый граф документа и отчёт о слиянии.
Для каждого шаблона создаётся отдельный подкаталог, в который
сохраняются исходный код и метаданные.

Для документов и шаблонов реализован общий *менеджер хранилища* —
программный интерфейс, инкапсулирующий все обращения к
персистентному хранилищу и предоставляющий единообразный набор
операций (получение объекта по идентификатору, добавление нового
объекта, удаление, переименование, перечисление). Реализация
менеджера выполнена через шаблонный класс, параметризуемый типом
объекта; конкретные менеджеры — для документов и для шаблонов —
наследуют общий интерфейс и переопределяют необходимые операции.
Такое решение обеспечивает единообразие работы с разнородными
объектами и упрощает потенциальный переход на иной способ
хранения: для перехода к специализированной базе данных
достаточно заменить реализации менеджеров, не затрагивая
остальных частей системы.

Репозиторий онтологии реализован как самостоятельная подсистема,
отвечающая за работу с хранилищем онтологической модели. Помимо
непосредственно хранения схемы и истории документов, репозиторий
выполняет полную сборку онтологической модели по истории, реализует
политики слияния значений предикатов, ведёт журнал событий слияния,
вычисляет состояние модели после переобработки документа.

Существенным аспектом реализации репозитория является механизм
*ленивой пересборки модели с кэшированием по отпечатку истории*.
Полная сборка модели — относительно затратная операция: она
требует прохождения по всей истории добавления документов,
последовательного применения политик слияния и обновления
индексов. Чтобы избежать повторного выполнения сборки при
многократных запросах, в репозитории поддерживается кэш,
индексируемый отпечатком текущего состояния истории документов.
Отпечаток вычисляется как криптографический хеш от
сериализованного представления списка записей истории; при
совпадении отпечатка с предыдущим возвращается ранее собранная
модель. При любом изменении истории отпечаток изменяется, и
последующий запрос приведёт к новой сборке модели.

Журнал событий слияния реализован в виде append-only файла, в
котором каждая строка соответствует одному событию: добавлению
факта, отзыву факта, отклонению факта. Каждая запись журнала
содержит полный контекст события: триплет в стандартной нотации,
идентификатор документа-источника, идентификатор шаблона, политику
слияния, эффективную дату, время добавления, причину отзыва (для
событий отзыва факта). Журнал представляет собой производный
индекс: при необходимости он может быть полностью пересобран по
истории документов, что обеспечивает устойчивость системы при
повреждении журнала.

## 3.6 Пользовательский интерфейс

### 3.6.1 Общая компоновка

Графический интерфейс системы организован в виде главного окна с
тремя тематическими вкладками, соответствующими трём основным
сущностям, с которыми работает пользователь: документам, шаблонам
и онтологической модели. Между вкладками реализована двусторонняя
навигация: например, из карточки индивида в онтологии можно
перейти к документу, послужившему источником конкретного факта; из
вкладки документа можно перейти к коду шаблона, по которому
извлечены поля; из карточки документа можно перейти к шаблону,
определившему его обработку.

Реализация интерфейса опирается на единые программные средства
оформления, инкапсулирующие палитры цветов и стили виджетов в
виде констант. Это обеспечивает визуальное единство всех частей
интерфейса и упрощает потенциальную смену оформления.

### 3.6.2 Вкладка работы с документами

Вкладка работы с документами организована как двухпанельный
интерфейс. Левая панель содержит список документов системы с
фильтрацией по статусу обработки. Правая панель отображает выбранный
документ с возможностью переключения между тремя тематическими
суб-вкладками.

*Суб-вкладка оригинала* отображает первую страницу исходного
документа в виде PDF (для удобного предпросмотра без необходимости
переключения в стороннюю программу) и предоставляет кнопку
открытия документа в системной программе по умолчанию для
полноценного просмотра.

*Суб-вкладка унифицированного представления* отображает результат
работы первой стадии конвейера в двух режимах: HTML-представление,
сохраняющее иерархическую структуру документа, и текстовое
представление дерева, явно показывающее иерархию элементов с
отступами. Оба режима подсвечивают типы элементов и
структурные блоки, что позволяет пользователю сопоставить
структуру документа с правилами шаблона.

*Суб-вкладка графа фактов* организована как двухпанельный
редактор. Левая часть отображает список узлов и триплетов
чернового графа; неполные узлы и переопределённые пользователем
выделены особым цветом для удобства восприятия. Правая часть
содержит форму редактирования выбранного узла или триплета. В
нижней части суб-вкладки расположены диалоги дополнительных
операций. Диалог *источника факта* для каждого узла графа
показывает, из какого поля шаблона он получен, и позволяет
перейти к коду шаблона. Диалог *генерации индивида* предоставляет
возможность создать индивид заданного концепта по введённому
вручную значению — это используется при ручном дополнении графа
фактами, не покрытыми шаблоном.

Над всеми суб-вкладками размещён индикатор статуса обработки
документа, показывающий пройденные стадии конвейера, кнопка
запуска (или продолжения) обработки и кнопка сброса с повторной
обработкой. Доступность кнопок зависит от текущего статуса
документа; например, кнопка продолжения обработки активна только
если документ не дошёл до последней стадии.

### 3.6.3 Вкладка работы с шаблонами

Вкладка работы с шаблонами также организована как двухпанельный
интерфейс. Левая панель содержит список шаблонов системы. Правая
панель отображает выбранный шаблон в виде карточки с описанием,
подсвеченным синтаксисом исходного кодом шаблона, отчётом о
структурной валидации и набором кнопок, выполняющих основные
операции с шаблоном.

Кнопка *генерации шаблона* запускает многошаговый сценарий
автоматизированной генерации, описанный в разделе 3.4.1, с
последовательным выполнением шагов и отображением промежуточных
результатов пользователю. Кнопка *открытия в редакторе* запускает
внешнюю программу редактирования с открытием файла кода
шаблона. Кнопка *удаления* удаляет шаблон системы вместе со всеми
связанными данными.

Подсветка синтаксиса исходного кода шаблона выполнена с помощью
известной библиотеки подсветки кода с преобразованием результата в
HTML-разметку, отображаемую средствами библиотеки виджетов.
Поддерживаются все основные конструкции языка, что облегчает
визуальный анализ кода в графическом интерфейсе.

### 3.6.4 Вкладка работы с онтологической моделью

Вкладка работы с онтологической моделью отображает текущее
состояние общей модели кафедры. Левая панель содержит иерархию
классов и список индивидов; иерархия классов извлекается из
схемы онтологии. Правая панель отображает выбранный класс или
индивид в виде *карточки*: для индивида показываются его свойства
(объектные и литеральные), обратные ссылки от других индивидов,
текстовые ссылки между карточками индивидов, для класса — состав
свойств, иерархия наследования, перечень индивидов класса.

Для каждого факта, отображаемого в карточке, доступен диалог
*источника факта*, показывающий, из какого документа и какого
шаблона факт был извлечён, и предлагающий перейти к
соответствующему документу. Этот механизм является ключевым
инструментом отслеживания происхождения фактов, необходимым для
проверки и аудита модели.

### 3.6.5 Известные ограничения интерфейса

Графический интерфейс реализован в синхронной модели обработки
событий: длительные операции (обращение к языковой модели,
многошаговая генерация шаблона, прогон конвейера на крупном
документе) приводят к временной невосприимчивости главного окна.
Это известное ограничение, оставленное на дальнейшее развитие
системы. Переход к асинхронной модели обработки длительных
операций является естественным направлением улучшения интерфейса
без изменения остальных частей системы.

## 3.7 Апробация системы

### 3.7.1 Набор тестовых документов

Качественная апробация системы проводилась на наборе реальных
документов кафедры. Состав набора подобран таким образом, чтобы
охватить все основные типы документов учебного процесса, с
которыми система предполагает работать в эксплуатации. Имена
участников учебного процесса в описании результатов обезличены.
Перечень обработанных документов включает:

- *заявление обучающегося о теме выпускной квалификационной
  работы*;
- *заявления обучающегося на практику* за два разных семестра — для
  оценки работы системы на структурно близких, но не
  тождественных документах;
- *индивидуальное задание на практику*;
- *отчёт руководителя практики* о результатах прохождения
  практики обучающимся;
- *тезисы двух студенческих научных конференций*.

Перечисленные документы получены от одного и того же обучающегося
кафедры, что обеспечивает наличие в полученной онтологической
модели согласованных перекрёстных ссылок на одного и того же
индивида (обучающегося, его руководителей, профильную
организацию, направление подготовки).

### 3.7.2 Проверенные сценарии

В рамках апробации проверены несколько сценариев работы системы,
охватывающих основные функциональные возможности.

*Сценарий полного цикла обработки документа.* Каждый из документов
тестового набора был проведён через полный цикл обработки от
загрузки в систему до записи извлечённых фактов в общую
онтологическую модель. По результатам прохождения зафиксировано:
для всех документов конвейер успешно достиг последней стадии;
ручное вмешательство в процесс не требовалось; графы фактов всех
документов оказались полными и синтаксически корректными; интеграция
в общую модель прошла без нарушений целостности. Полученная по
итогам обработки общая модель содержит согласованные между собой
сведения о студенте, его выпускной работе, прохождении практик в
двух семестрах, его научных публикациях, направлении подготовки и
профиле, учебной группе, профильных организациях прохождения
практики, руководителях.

*Сценарий кросс-форматного теста.* Один из документов тестового
набора был обработан в трёх форматах: исходный документ в формате
DOCX, преобразованный к формату DOC, преобразованный к формату
PDF. Унифицированные представления, полученные из всех трёх версий,
были сопоставлены между собой; результаты извлечения полей и
итоговые графы фактов оказались идентичны с точностью до
канонической формы. Этот результат подтверждает архитектурное
свойство форматной независимости правил извлечения, обоснованное
в разделе 2.1.1.

*Сценарий обработки структурно близких документов одним шаблоном.*
Два заявления на практику, отличающиеся семестром и
сопровождающимися сведениями, были обработаны под управлением
одного шаблона. В первом случае декларативная часть шаблона
справилась полностью, и языковая модель лишь подтвердила
извлечённые значения. Во втором случае несколько полей оказались
извлечены не декларативной частью, а коррекцией языковой модели:
структура документа имела локальный сдвиг, не учтённый правилами
шаблона. Полученные графы фактов в обоих случаях оказались полными
и согласованными. Этот результат иллюстрирует ценность гибридной
экстракции: коррекция языковой моделью позволила обработать
документ, для которого декларативные правила оказались неточны, без
правки шаблона.

*Сценарий ручного редактирования графа.* На примере одного из
документов проведено ручное редактирование чернового графа через
графический интерфейс: создание дополнительного узла индивида с
заданным концептом, добавление триплета связи нового индивида с
существующим, исключение ложноположительного триплета,
переопределение значения литерала. Внесённые правки были сохранены;
при последующем повторном прогоне стадии построения графа правки
сохранились (поскольку результат шаблона остался согласованным с
ними) и были применены к новому черновику.

### 3.7.3 Качественная оценка результатов

По итогам апробации можно сделать следующие качественные выводы.

*Функциональная полнота.* Все функциональные требования,
сформулированные в разделе 1.5.1, реализованы и подтверждены
работой на реальных документах. Полный цикл обработки документа
проходит без необходимости ручного вмешательства в типичных
случаях; ручное редактирование графа доступно через графический
интерфейс; ручное указание класса документа возможно при
необходимости; интеграция в общую модель кафедры выполняется с
учётом политик слияния значений; происхождение каждого факта
сохраняется и доступно для просмотра.

*Соответствие нефункциональным требованиям.* Воспроизводимость
обработки подтверждена многократными прогонами одних и тех же
документов: декларативные части извлечения дают совпадающие
результаты; коррекции языковой модели (за исключением случаев
сдвига структуры) также воспроизводимы. Объяснимость результатов
обеспечена сохранением полной истории извлечения каждого поля и
доступностью её просмотра в графическом интерфейсе.
Расширяемость подтверждена опытом разработки шаблонов для разных
классов документов: подключение нового типа документа выполняется
добавлением шаблона без изменения других частей системы.

*Сильные стороны гибридной экстракции.* Опыт эксплуатации
подтвердил основной тезис, обоснованный в главе 1: гибридный
подход «детерминированные правила плюс коррекция языковой
моделью» эффективно сочетает воспроизводимость и устойчивость к
вариативности оформления документов. Случаи, в которых
декларативные правила оказались неточны, успешно компенсируются
коррекцией языковой модели; при этом основная масса значений
извлекается детерминированной частью, обеспечивая прозрачность
процесса.

*Замечания и направления улучшения.* Опыт эксплуатации также
выявил ряд аспектов, требующих внимания. Качество автоматической
генерации шаблонов сильно зависит от того, насколько новый класс
документа похож на ранее виденные; для классов, существенно
отличающихся от типичных, доля ручной правки шаблона существенно
возрастает. Структурная валидация шаблона выявляет большинство
типовых проблем, однако некоторые ошибки логики связывания фактов
обнаруживаются только в процессе работы с реальными документами. В
случае необычных формулировок дат разбор эффективной даты документа
может оказаться неудачным, что в свою очередь делает невозможным
корректное применение политики «замены по дате».

Отдельно следует подчеркнуть, какие свойства системы в рамках
апробации *не* проверялись и поэтому не должны выдаваться за
достижения. Не выполнялся расчёт количественных метрик качества
извлечения (точность, полнота, F-мера) в силу отсутствия
размеченного корпуса. Не проверялась работа на сложных
сканированных документах, требующих оптического распознавания
символов. Не проверялся многопользовательский режим работы с
общей онтологической моделью. Не проверялась обработка очень
крупных документов (объёмом в сотни страниц). Не проверялась
устойчивость генерации шаблонов для классов документов, сильно
отличающихся от ранее обработанных языковой моделью. Эти
направления зафиксированы как перспективы дальнейшего развития
системы (см. раздел 3.8).

## 3.8 Ограничения и направления развития

По результатам разработки и апробации системы могут быть
систематизированы её известные ограничения и определены
направления дальнейшего развития. Перечисленные ограничения не
являются недостатками реализации в собственном смысле слова; часть
из них представляет собой сознательно принятые при проектировании
компромиссы (см. раздел 1.5.3), часть — естественные направления
расширения функциональности.

**Ограничения, связанные с поддерживаемыми форматами.** В текущей
реализации поддерживаются только электронные текстовые документы
(DOC, DOCX) и документы PDF с текстовым слоем. Сканированные
документы, требующие оптического распознавания символов, не
обрабатываются. Архитектура системы заложена с расчётом на
возможность подключения внешних модулей оптического распознавания
в качестве *внешних извлекателей данных* (см. раздел 2.3.2);
конкретная интеграция с одной из существующих систем оптического
распознавания может быть выполнена без изменения остальных частей
системы.

**Ограничения, связанные со средой исполнения шаблонов.**
Безопасность исполнения шаблонов обеспечивается статическим
анализом исходного кода и ограничением списка разрешённых
импортируемых модулей; отдельная программная песочница не
реализована. Введение полноценной песочницы является целесообразным
направлением развития при переходе системы к режиму, в котором
шаблоны разрабатываются менее доверенными участниками. Возможные
варианты реализации песочницы включают применение
специализированных интерпретаторов с ограниченным набором операций,
запуск кода в изолированных подпроцессах с контролируемыми
правами доступа, использование стандартных средств контейнеризации.

**Ограничения, связанные с режимом эксплуатации.** Система
ориентирована на однопользовательский режим работы с локальным
хранением данных; параллельный доступ нескольких пользователей к
одной онтологической модели не поддерживается. Переход к
многопользовательскому режиму потребует введения механизмов
блокировок или транзакционного слоя поверх онтологической модели,
а также пересмотра графического интерфейса в части совместного
редактирования. Параллельным направлением является переход от
локального файлового хранения к централизованному, в том числе с
переносом онтологической модели в специализированное хранилище
RDF-триплетов; такое расширение упрощается архитектурным
разделением слоёв, заложенным в системе.

**Ограничения, связанные с пакетной обработкой.** Графический
интерфейс системы предполагает обработку документов по одному;
встроенного механизма пакетной обработки нескольких документов
через интерфейс не реализовано. Сам конвейер обработки технически
допускает пакетный запуск программно, без участия графического
интерфейса; однако удобный пользовательский сценарий пакетной
обработки требует отдельной разработки.

**Ограничения, связанные с оценкой качества.** Оценка качества
работы системы в настоящей работе носит качественный, а не
статистический характер. Формирование размеченного корпуса
документов с эталонными значениями всех извлекаемых полей и
расчёт количественных метрик (точности, полноты, F-меры)
является самостоятельной исследовательской задачей; в рамках
настоящей работы такая задача не ставилась. Проведение расширенной
апробации на размеченном корпусе документов нескольких студентов
кафедры зафиксировано как самостоятельное направление дальнейшего
развития работы.

**Ограничения, связанные с подсистемой языковой модели.**
Используется коммерческая большая языковая модель через её
программный интерфейс, что подразумевает зависимость от
доступности внешнего сервиса и стоимость обращений. Для случаев,
когда такая зависимость нежелательна, целесообразным
направлением развития является поддержка работы с локально
развёрнутыми языковыми моделями, доступными в виде совместимых
программных интерфейсов. Дополнительными направлениями
оптимизации подсистемы языковой модели являются введение
кэширования запросов, учёта стоимости и потребления токенов,
а также использование потоковой выдачи ответа для длительных
запросов.

**Ограничения, связанные с проверкой логической согласованности
модели.** Контроль целостности онтологической модели выполняется
на синтаксическом уровне (проверка соответствия областям
определения и значения предикатов, проверка единственности
значений по политикам слияния). Полноценный логический вывод с
использованием семантики OWL не задействован. Применение
машины логического вывода (reasoner) позволило бы расширить
возможности контроля и могло бы использоваться для проверки
согласованности новых фактов с уже накопленными до их добавления
в модель.

Перечисленные ограничения и направления развития составляют
естественную программу дальнейшего совершенствования системы.
Принятая архитектура с разделением системы на функционально
независимые модули обеспечивает возможность последовательного
устранения каждого из ограничений без необходимости полной
переработки системы.
