**Python 3.11** выбран в качестве основного языка, поскольку он
одновременно является и языком приложения, и языком, на котором
пишутся пользовательские шаблоны извлечения. Использование одного
языка устраняет необходимость в разработке отдельного
домен-специфичного формата шаблонов и снижает порог входа для их
авторов; кроме того, в экосистеме Python имеются зрелые библиотеки
для всех ключевых подзадач системы — работы с RDF (rdflib),
морфологического разбора русского языка (pymorphy3), разбора
XML-структуры DOCX (стандартные `xml.etree` и `zipfile`).

**rdflib** используется только как внутренний контейнер итогового
RDF-графа документа, передаваемого в репозиторий онтологии. Сам
процесс сборки графа в шаблоне идёт не через rdflib, а через
собственный построитель графа `TemplateGraphBuilder`, который
скрывает работу с триплетами за операциями уровня предметной
области (см. главу 2, раздел 2.7). Это разделение позволило
сократить набор операций, доступных автору шаблона, до минимально
необходимого и устранить ошибки, типичные при прямой работе с
rdflib (неконсистентные пространства имён, неправильно
типизированные литералы).

**pymorphy3** применяется для приведения частей ФИО к именительному падежу. 
Без морфологической нормализации один и тот же человек, упомянутый в
разных документах в разных падежах, получал бы разные
идентификаторы и не объединялся бы в один индивид. Подробнее
устройство этого концепта обсуждается в подразделе 3.2.3.

Преобразование документов формата **DOC** к формату DOCX выполнено
через цепочку fallback: первой попыткой запускается LibreOffice
(`soffice --headless`), при его отсутствии в системе — Microsoft
Word через COM-интерфейс (через библиотеку `pywin32`). Цепочка
выбрана так, чтобы преобразование работало в типовой среде
кафедры без специальной настройки: на компьютерах сотрудников, как
правило, установлен Microsoft Office; на машинах разработчика и в
автоматизированных средах — LibreOffice.

В качестве **большой языковой модели** по умолчанию используется
`gpt-5.4-mini` через официальный SDK OpenAI. Имя модели вынесено в
константу настроек приложения, что позволяет заменить её без
изменения программного кода. Выбор обоснован соотношением
качества и стоимости: для задачи проверки уже извлечённых
шаблоном значений и поиска недостающих не требуется наиболее
крупная модель, а задержки и затраты заметно ниже.

### 3.2.1 Контекст документа: ленивая загрузка с автоматическим освобождением ресурсов

Конвейер обработки оперирует разнородными по объёму данными: для
крупного документа унифицированное представление, результат
извлечения полей, черновой граф фактов и загруженный код шаблона
суммарно могут занимать существенный объём оперативной памяти.
Передача этих данных через все уровни вызовов в виде явных
параметров затрудняла бы сигнатуры функций и приводила бы к
загрузке заведомо ненужных данных.

Для решения этой задачи введён программный объект — *контекст
документа* (`DocumentContext`), — обеспечивающий ленивую загрузку
данных по требованию и их автоматическое освобождение по
завершении обработки. Каждое тяжёлое поле контекста объявлено
парой свойств `@property` и `@property.setter`: при первом
обращении к полю выполняется чтение из соответствующего файла, при
последующих — возврат закэшированного значения, при присваивании —
замена кэша. Для гарантированного освобождения ресурсов объявлен
менеджер контекста, оборачивающий весь жизненный цикл обработки
документа:

```python
class DocumentContext:
    def __init__(self, doc: Document):
        self.document: Document = doc
        self._uddm: Optional[UDDM] = None
        self._extr_res: Optional[ExtractionResult] = None
        self._draft_graph: Optional[DraftGraph] = None
        self._template_ctx: Optional[TemplateContext] = None

    @property
    def uddm(self) -> Optional[UDDM]:
        if self._uddm is not None:
            return self._uddm
        try:
            self._uddm = UDDM.load(self.document.uddm_file_path())
            return self._uddm
        except Exception:
            return None

    @uddm.setter
    def uddm(self, uddm: Optional[UDDM]):
        self._uddm = uddm

    # ... аналогичные пары свойств для extraction_result, draft_graph,
    # template_ctx ...

    def unload(self):
        self._uddm = None
        self._extr_res = None
        self._draft_graph = None
        if self._template_ctx:
            self._template_ctx.unload()
            self._template_ctx = None


@contextmanager
def document_context(doc: Document):
    ctx = DocumentContext(doc)
    try:
        yield ctx
    finally:
        ctx.unload()
```

Использование контекста на уровне конвейера сводится к одной
обёртке `with`, после выхода из которой все тяжёлые объекты
автоматически освобождаются:

```python
with document_context(doc) as ctx:
    return self._full_run(ctx, final_stage)
```

Решение даёт три практически важных свойства одновременно:
прозрачность сигнатур (модули конвейера принимают единственный
аргумент `ctx`); экономию памяти (модули, которым некоторое поле
контекста не нужно, никогда не вызывают чтения соответствующего
файла); гарантированное освобождение ресурсов независимо от пути
выхода (исключение, ранний `return` и т. п.).

### 3.2.2 Реестр преобразований форматов

Поддержка нескольких типов преобразований документов между
форматами и в унифицированное представление организована через
программный реестр `ConverterRegistry`. Реестр разделяет три
категории преобразований: нормализаторы между форматами без потерь,
внутренние конвертеры в унифицированное представление, внешние
извлекатели данных:

```python
class ConverterRegistry:
    normalizers: Dict[str, Type[BaseNormalizer]] = {}
    internal_converters: Dict[str, Type[BaseInternalConverter]] = {}
    external_converters: Dict[str, Type[BaseExternalConverter]] = {}

    normalizers["doc"] = DocToDocx
    normalizers["pdf"] = PdfToDocx
    internal_converters["docx"] = DocxToUDDM
```

Подключение поддержки нового формата требует одной строки в
инициализации реестра и реализации соответствующего класса
преобразования; остальные части системы не затрагиваются. Если
для входного формата существует нормализующее преобразование, оно
применяется первым; результат рекурсивно проверяется, и преобразования
продолжаются до тех пор, пока формат документа не стабилизируется.
После стабилизации управление передаётся внутреннему конвертеру либо,
при его отсутствии, внешнему извлекателю с адаптером в унифицированное
представление.

Текущий состав реестра отражает реализованную поддержку: внутренний
конвертер `DocxToUDDM` обходит XML-структуру файла DOCX и формирует
унифицированное представление; нормализаторы `DocToDocx` и
`PdfToDocx` сводят документы соответствующих форматов к DOCX, после
чего вступает в работу основной конвертер. Слот для внешних
извлекателей данных в текущей версии остаётся незаполненным — он
предусмотрен для подключения средств оптического распознавания
символов.

### 3.2.3 Морфологическое приведение ФИО к именительному падежу

Концепт `PersonConcept` отвечает за идентификацию индивидов класса
*Персона*. Стратегия идентификации — хеш от ключа, образованного
фамилией и инициалами имени и отчества. Чтобы один и тот же человек,
упомянутый в одном документе как «направить Соломенникову Николаю
Александровичу», а в другом — как «студент Соломенников Николай
Александрович», получил один и тот же идентификатор, все три части
ФИО приводятся к именительному падежу до вычисления ключа.

Морфологический разбор выполняется средствами библиотеки pymorphy3.
Однако прямое применение её результата приводит к ошибкам: для
большинства частей ФИО анализатор возвращает несколько вариантов
разбора, и без дополнительного критерия может быть выбран
омонимичный «не-ФИО» вариант. Например, фамилия «Соломенников» без
дополнительной фильтрации читается как множественное число от
существительного «соломенник» и приводится к форме «Соломенники».
Чтобы этого избежать, среди возвращаемых вариантов отбираются
только те, у которых в грамматических признаках присутствует
соответствующий тег фамилии, имени или отчества:

```python
_PART_TAG = {
    "surname": "Surn",
    "first":   "Name",
    "patronymic": "Patr",
}

parses = _morph.parse(cleaned)
typed = [p for p in parses if target_tag in p.tag]
if not typed:
    return cleaned  # надёжного разбора нет — оставляем как есть
```

Дополнительно учитывается *омонимия по полу*: «Соломенникова
Николая» — это родительный падеж мужского имени, но та же фамилия
в начальной форме может принадлежать женщине; «Иванова» в одном
документе может оказаться женской формой «Иванов», в другом —
фамилией Ивановой. Чтобы предпочесть согласованный по полу вариант
разбора, перед нормализацией фамилии и отчества определяется пол по
имени, и при сортировке вариантов разбора предпочтение отдаётся
варианту с соответствующим полом.

Идемпотентность парсинга обеспечивается тем, что слова, уже
находящиеся в именительном падеже, попадают в фильтр типизированных
разборов и возвращаются без изменений. Это критически важно для
повторных проходов: повторная обработка того же документа
гарантированно даёт те же идентификаторы индивидов.

Существенное проектное решение касается *состава ключа
хеширования*. На вход хеширования подаётся не полное ФИО, а
сочетание фамилии в нижнем регистре и инициалов имени и отчества:

```python
sort_key = f"{last_norm.lower()}|{first_init}|{middle_init}"
return f"Персона_{short_sha1(sort_key)}"
```

Это устраняет существенную в реальных документах проблему: один и
тот же человек в разных документах может быть упомянут полным
именем (например, в заявлении) и инициалами (например, в подписи
руководителя). Если бы ключ содержал полные имя и отчество, такие
упоминания получили бы разные идентификаторы. Свёртка имени и
отчества к инициалам объединяет их в одного индивида при крайне
маловероятной коллизии в пределах одной кафедры.

### 3.2.4 Структурная валидация шаблона через статический анализ

Структурная валидация шаблона выполняется до его использования и
включает шесть категорий проверок (см. главу 2, раздел 2.4.3). Из
них наиболее технически интересны категории безопасности и
согласованности с онтологией, реализованные через анализ
абстрактного синтаксического дерева исходного кода.

Безопасность реализуется через обход дерева с проверкой трёх типов
узлов: импортов, вызовов и обращений к атрибутам. Списки
запрещённых имён зафиксированы в виде констант с пояснением
конкретной угрозы каждого имени:

```python
_FORBIDDEN_IMPORT_ROOTS = {
    "os":         "доступ к файловой системе и переменным окружения",
    "subprocess": "запуск внешних процессов",
    "socket":     "сетевые соединения",
    "urllib":     "сетевые соединения",
    "pickle":     "десериализация произвольных объектов",
    # ... и так далее
}
_FORBIDDEN_BUILTIN_CALLS = {
    "open":  "запись/чтение файлов",
    "exec":  "выполнение произвольного кода",
    "eval":  "выполнение произвольных выражений",
    "__import__": "динамический импорт",
    # ...
}
_FORBIDDEN_ATTRIBUTES = {
    "__subclasses__", "__globals__", "__builtins__",
    # ...  типичные точки обхода ограничений интерпретатора Python
}
```

Каждое обнаруженное замечание помечается уровнем важности
(«ошибка» или «предупреждение») и снабжается ссылкой на номер
строки и колонки в исходном коде шаблона. Сводный отчёт
отображается в графическом интерфейсе в карточке шаблона.

Категория согласованности с онтологией реализована аналогичным
обходом дерева: из исходного кода извлекаются все обращения к
объекту `ONTO` (программное представление пространства имён
онтологии) — как через атрибут (`ONTO.Студент`), так и через индекс
(`ONTO["имеетВКР"]`). Имена сверяются с фактическим перечнем
терминов, объявленных в схеме онтологии. При обнаружении
несовпадения выдаётся предупреждение с подсказкой ближайшего по
написанию имени, что облегчает обнаружение опечаток автору
шаблона:

```
WARN/ontology: ONTO.Студенгт не найдено в онтологии.
               Возможно, имелось в виду ONTO.Студент?
```

### 3.2.5 Контракт ответа языковой модели

Существенным аспектом подсистемы взаимодействия с языковой
моделью является детальная формализация контракта ответа. Опыт
реализации показал, что качество структурированного ответа модели
определяется не столько её способностями, сколько детальностью
описания контракта в системном промпте: при недостаточной
формализации модель регулярно возвращала неоднозначные ответы,
которые невозможно было однозначно разобрать.

В выработанном виде системный промпт для извлечения/коррекции полей 
формулирует пять допустимых сценариев исхода для каждого поля и явный 
инвариант, исключающий комбинации значений, не предусмотренные сценариями:

```
Сценарии (СТРОГО следуй им — другие комбинации запрещены):

1. template.value присутствует и корректно (изменения не нужны):
   status = true, value = null, error = null

2. template.value присутствует, но некорректно;
   правильное значение найдено:
   status = true, value = "новое значение", error = "что было не так"

3. template.value присутствует, но некорректно;
   правильное найти не удалось:
   status = false, value = null, error = "что пошло не так"

4. template.value отсутствует (null), значение в документе найдено:
   status = true, value = "значение", error = null

5. template.value отсутствует и значение не найдено:
   status = false, value = null, error = "ошибка"

ИНВАРИАНТ:
 — Если status=true И template.value=null → value ОБЯЗАН быть строкой.
 — Если status=true → value либо null (подтверждение), либо непустая строка.
 — Если status=false → value ОБЯЗАН быть null.
 — value=null при status=true НЕ означает «значение не найдено» —
   это значит «template.value уже верный».
```

Разбор ответа на стороне приложения использует сценарную таблицу
напрямую: для каждого поля проверяются значения `status` и `value`
и применяется ровно тот переход, который предписан системой
сценариев. Любое отклонение фиксируется как непредвиденная ошибка
этапа коррекции, а итоговое значение поля выбирается по приоритету
из результата детерминированного этапа.

### 3.2.6 Политики слияния как декларативные аннотации схемы

Политика слияния значений каждого предиката онтологии хранится
непосредственно в TBox в виде аннотации `:mergePolicy`. Это
позволяет менять поведение слияния отдельных свойств без правки
программного кода. Аннотация представляет собой именованный
индивид одного из трёх допустимых перечислений:

```turtle
:обучаетсяВГруппе a owl:ObjectProperty ;
    rdfs:domain :Студент ;
    rdfs:range :Группа ;
    :mergePolicy :Policy_SetByDate .

:телефон a owl:DatatypeProperty ;
    rdfs:domain :Персона ;
    rdfs:range xsd:string ;
    :mergePolicy :Policy_Add .

:авторВКР a owl:ObjectProperty ;
    rdfs:domain :ВКР ;
    rdfs:range :Студент ;
    :mergePolicy :Policy_Set .
```

При запуске приложения репозиторий онтологии один раз обходит схему
и формирует словарь «предикат → политика слияния», который затем
используется при каждом слиянии нового документа. Свойства, для
которых аннотация не задана, получают политику по умолчанию —
*добавление*, что обеспечивает безопасное поведение при добавлении
новых свойств в онтологию: появление нового предиката не требует
правки модуля интеграции.

Журнал событий слияния, ведущийся в формате JSON Lines, записывает
для каждого добавленного, отозванного или отклонённого факта
полный контекст: идентификатор документа, шаблона, эффективную дату,
применённую политику слияния, причину отзыва. Этот журнал
позволяет в любой момент восстановить происхождение каждого
факта в общей модели; кроме того, он может быть полностью
пересобран по истории документов, если оказывается повреждён.

## 3.3 Пользовательский интерфейс

Графический интерфейс реализован средствами библиотеки PySide6 и
организован как единое окно с тремя тематическими вкладками:
*Документы*, *Шаблоны*, *Онтология*. Каждая вкладка построена по
схеме «двухпанельный контейнер»: слева — список объектов, справа —
карточка выбранного объекта. Между вкладками реализована
двусторонняя навигация: например, из карточки индивида в онтологии
можно перейти к документу-источнику конкретного факта, а из
вкладки документа — к коду шаблона, по которому извлечены поля.

Ниже выделены два узла интерфейса, заслуживающие отдельного
обсуждения.

### 3.3.1 Редактор графа фактов

Вкладка документа содержит три суб-вкладки: *Оригинал* (предпросмотр
первой страницы PDF-конверсии и кнопка открытия документа в системной
программе), *UDDM* (отображение унифицированного представления в
режимах HTML и tree-view с подсветкой структуры) и *Граф*
(двухпанельный редактор чернового графа). Наибольший
функциональный интерес представляет именно редактор графа.

Левая часть редактора отображает список узлов и триплетов
чернового графа. Полные триплеты показываются обычным
оформлением; неполные триплеты выделяются цветом, явно показывая
пользователю, какие именно факты не удалось построить
автоматически. Переопределённые триплеты (для которых
пользователь задал замену через слой правок) также выделяются
отличающимся цветом. Правая часть содержит форму редактирования
выбранного узла или триплета: для узла — ввод значения, 
для триплета — управление включением и исключением.

Вверху страницы расположен индикатор статуса документа,
показывающий пройденные стадии конвейера, а также кнопки запуска
обработки и сброса с повторной обработкой. Доступность кнопок
зависит от текущего статуса: например, кнопка продолжения
обработки активна только тогда, когда документ не дошёл до
последней стадии.

### 3.3.2 Источник факта: отслеживание происхождения

Каждый узел графа в редакторе ассоциирован с *источником* — именем
поля шаблона, из которого был получен соответствующий узел. По
кнопке «Источник факта» открывается диалог, показывающий
поле-источник и предлагающий перейти к коду шаблона.

Аналогичный механизм реализован на вкладке онтологии. Каждый факт
в карточке индивида или класса доступен для просмотра
происхождения: открывающийся диалог отображает документ,
из которого пришёл факт, шаблон, по которому он был извлечён,
эффективную дату документа, применённую при слиянии политику и —
при наличии — отзыв и причину отзыва конкурирующего факта. Из
диалога возможен переход к самому документу: пользователь
оказывается на нужной вкладке с открытой карточкой документа.

Описанный механизм является ключевым инструментом проверки и
аудита онтологической модели. В сочетании с журналом событий
слияния (см. подраздел 3.2.6) он обеспечивает полную
прослеживаемость каждого факта от его представления в общей
модели до конкретного фрагмента исходного документа.

### 3.3.3 Известные ограничения интерфейса

Интерфейс реализован в синхронной модели обработки событий:
длительные операции (обращение к языковой модели, многошаговая
генерация шаблона, прогон конвейера на крупном документе)
приводят к временной невосприимчивости главного окна. Это
известное ограничение, которое естественно устранить переводом
длительных операций в рабочие потоки или асинхронные задачи без
изменения остальной части системы.

## 3.4 Апробация системы

Качественная апробация разработанной системы проводилась на
наборе реальных документов кафедры. Поскольку количественные
метрики качества извлечения требуют размеченного корпуса,
формирование которого выходит за рамки настоящей работы, здесь
представлена качественная оценка результатов работы системы на
типичных сценариях её использования.

### 3.4.1 Тестовый набор документов

Состав тестового набора подобран таким образом, чтобы охватить
основные типы документов учебного процесса, с которыми
предполагается работа системы в эксплуатации. Все документы
относятся к одному и тому же обучающемуся кафедры, что
обеспечивает наличие в полученной онтологической модели
согласованных перекрёстных ссылок на одного и того же индивида.
Имена участников учебного процесса при описании результатов
обезличены.

Перечень обработанных документов:

- заявление обучающегося о теме выпускной квалификационной работы;
- два заявления обучающегося на практику (за разные семестры);
- индивидуальное задание на практику;
- отчёт руководителя практики;
- тезисы двух студенческих научных конференций.

### 3.4.2 Проверенные сценарии

**Полный цикл обработки.** Каждый документ из тестового набора был
проведён через все пять стадий конвейера от загрузки исходного
файла до записи фактов в общую модель. Для всех документов
конвейер достиг последней стадии без необходимости ручного
вмешательства; графы фактов оказались полными и синтаксически
корректными; интеграция в общую модель прошла без нарушений
целостности. Полученная по итогам обработки общая онтологическая
модель содержит согласованные сведения о студенте, его выпускной
работе, прохождении практик, научных публикациях, направлении
подготовки и профиле, учебной группе, профильных организациях
прохождения практики и руководителях.

**Кросс-форматный тест.** Один из документов тестового набора был
обработан в трёх форматах: исходный DOCX, преобразованный к DOC,
преобразованный к PDF. Унифицированные представления, полученные
из всех трёх версий, оказались идентичны для пары DOCX и DOC и
близки до уровня переноса абзацев для PDF; результаты извлечения
полей и итоговые графы фактов совпали с точностью до канонической
формы. Этот результат подтверждает свойство форматной
независимости правил извлечения, обоснованное в главе 2.

**Структурно близкие документы под одним шаблоном.** Два заявления
на практику, отличающиеся семестром и сопровождающимися сведениями,
обрабатывались под управлением одного шаблона. В первом случае
детерминированная часть извлечения справилась полностью, и
коррекция языковой моделью лишь подтвердила извлечённые значения.
Во втором случае несколько полей были «вытянуты» только этапом
коррекции: документ имел локальный сдвиг в структуре, не
учтённый правилами шаблона. Полученные графы фактов в обоих
случаях оказались полными. Этот сценарий иллюстрирует ценность
гибридной экстракции: коррекция языковой моделью позволила
обработать документ, для которого декларативные правила оказались
неточны, без правки шаблона. Также полезным оказалось применение
политик слияния: даже при смене порядка загрузки документов в 
итоговую онтологическую модель помадают только актуальные данные.

**Ручное редактирование графа.** На примере нескольких документов
проведено ручное редактирование чернового графа через графический
интерфейс: создание дополнительного индивида с выбранным концептом,
добавление триплета связи нового индивида с существующим,
исключение ложноположительного триплета, переопределение значения
литерала. Внесённые правки были сохранены; при последующем
повторном прогоне стадии построения графа правки сохранились
(поскольку результат шаблона остался согласованным с ними) и были
автоматически применены к новому черновику.

### 3.4.3 Качественная оценка результатов

По итогам апробации можно сделать следующие качественные выводы.

Полный цикл обработки документа проходит без необходимости
ручного вмешательства в типичных случаях. Все функциональные
требования, сформулированные в разделе 1.5.1, реализованы и
подтверждены работой на реальных документах кафедры.
Воспроизводимость детерминированной части подтверждена
многократными прогонами одних и тех же документов: декларативные
части извлечения дают совпадающие результаты, коррекции языковой
моделью в большинстве случаев также воспроизводимы.
Прослеживаемость каждого факта обеспечена сохранением полной
истории извлечения и доступностью её просмотра в графическом
интерфейсе.

Опыт эксплуатации подтвердил основной тезис, обоснованный в
главе 1: гибридный подход «детерминированные правила + коррекция
языковой моделью» эффективно сочетает воспроизводимость и
устойчивость к вариативности оформления документов. Случаи, в
которых декларативные правила оказываются неточны, успешно
компенсируются коррекцией языковой моделью; основная же масса
значений извлекается детерминированной частью, обеспечивая
прозрачность процесса и возможность аудита.

Среди особенностей реализации, замеченных в ходе апробации и
требующих внимания: качество автоматически сгенерированной
заготовки шаблона существенно зависит от того, насколько новый
класс документа похож на ранее виденные; в случае нестандартных
формулировок дат разбор эффективной даты документа может оказаться
неудачным, что препятствует корректному применению политики
«замены по дате»; некоторые ошибки в логике связывания фактов в
шаблоне обнаруживаются только в процессе работы с реальными
документами и не выявляются структурной валидацией.

В рамках апробации не проверялись и не должны
выдаваться за достижения: расчёт количественных метрик качества
извлечения (точности, полноты, F-меры) — в отсутствие
размеченного корпуса; работа на сложных сканированных документах,
требующих оптического распознавания символов; многопользовательский
режим работы с общей моделью; обработка очень крупных документов
(сотни страниц); устойчивость генерации шаблонов для классов
документов, существенно отличающихся от ранее обработанных
языковой моделью.

## 3.5 Известные ограничения и направления развития

По результатам разработки и апробации систематизированы известные
ограничения системы и определены направления её дальнейшего
развития. Большинство ограничений представляет собой сознательно
принятые при проектировании компромиссы и допускает устранение без
полной переработки системы благодаря модульному устройству
архитектуры.

К наиболее существенным направлениям развития относятся:

- **Поддержка сканированных документов.** Архитектура содержит
  каркас для подключения внешних извлекателей данных (см. раздел
  2.3.2); реализация интеграции с одной из существующих систем
  оптического распознавания символов выполняется в виде
  отдельного класса извлекателя без изменения остальных частей
  системы.
- **Песочница исполнения шаблонов.** Текущая реализация
  обеспечивает безопасность только статическим анализом
  исходного кода. Полноценная песочница (на основе
  специализированных интерпретаторов, изолированных подпроцессов
  с ограниченными правами или средств контейнеризации) расширила
  бы круг возможных авторов шаблонов до менее доверенных
  участников.
- **Многопользовательский режим.** Переход к одновременному
  доступу нескольких пользователей к общей онтологической модели
  потребует введения механизмов блокировок или транзакционного
  слоя поверх репозитория онтологии, а также пересмотра
  графического интерфейса в части совместного редактирования.
- **Замена локального хранения на специализированное хранилище
  RDF-триплетов.** Менеджеры хранилища изолируют остальные части
  системы от способа хранения; при росте объёма обрабатываемых
  данных целесообразно перенести онтологическую модель в
  выделенное triple-store-хранилище.
- **Поддержка локально развёрнутых языковых моделей.** Зависимость
  от внешнего сервиса коммерческого поставщика устраняется
  переходом к работе с языковыми моделями, доступными через
  совместимые программные интерфейсы.
- **Введение машины логического вывода.** Применение
  OWL-reasoner-а позволило бы расширить возможности контроля
  целостности модели и проверки согласованности новых фактов с
  уже накопленными до их добавления.
- **Расширенная апробация.** Формирование размеченного корпуса
  документов с эталонными значениями всех извлекаемых полей и
  расчёт количественных метрик качества являются самостоятельным
  направлением исследовательской работы.

Перечисленные направления составляют естественную программу
дальнейшего совершенствования системы. Принятая архитектура с
разделением на функционально независимые модули обеспечивает
возможность последовательного устранения каждого из ограничений
без необходимости полной переработки системы.
